### 0.2 产品新基线

1. **目标人群**：**个人创作者 + 2–10 人小团队**。保留服务端多租户工作区、邀请码与 `owner / editor / viewer` 角色隔离；后端保留云端部署以支撑小团队协同与公众号固定公网出口 IP。

## 1. 架构决策与执行手册：放弃并删除 `web/`、全力主攻桌面端

### 1.1 架构可行性评估与后期演化路线（为什么可行、以后怎么加回 Web）

1. **为什么现在删除 `web/` 是最正确的决定**：
   - `web/src`（185 文件、6.1 万行）与 `renderer/`（242 文件、10.2 万行）之间有 **182 个同名文件**、**166 vs 164 个双份 E2E**，每次改业务都要同步改两遍并过 `scripts/check-e2e-pairs.mjs`；
   - 个人 + 小团队成员统一安装 Electron 桌面端即可登录同一个云端工作区协同工作，外链审阅用服务端渲染预览页即可，现阶段**零真实必要维持两套前端代码**。
2. **后期从桌面端同源演化 Web 的实证依据**：
   - `renderer/` 本身就是纯前端技术栈（React 18 + Vite + Tailwind CSS + React Router v7 + TanStack Query），不直接引入 Electron/Node 主进程包；
   - [renderer/vite.config.ts](../renderer/vite.config.ts#L14-L87) 与 [renderer/package.json](../renderer/package.json#L8-L10) 已支持双构建模式：`vite build --mode desktop` 输出 `../desktop/renderer/` 并注入远端 API 基址；`vite build` 输出静态包 `renderer/dist/`；
   - 全部桌面专属能力均软挂载在 `window.opsDesktopUI?.xxx` 与 `isElectronDesktop()` 之后。
   - **后期演进方案**：未来重新需要 Web 端时，**绝不再新建 `web/` 目录**，而是在 `renderer/lib/platform-bridge.ts` 抽象环境适配层（桌面走 IPC，浏览器走云端降级），一套源码通过 `--mode desktop` 与 `--mode web` 产出双目标构建。

### 1.2 从现在起必须遵守的 3 条“保留未来 Web 可演化性”代码纪律

1. **桌面 IPC 调用收口**：后续新写代码对 `window.opsDesktopUI` 的访问，尽量集中放在 `renderer/lib/platform-bridge.ts` 封装函数中，不要到处散写硬耦合判断，保证浏览器环境下能安全返回 `supported: false`。
2. **保持基本响应式布局**：桌面端主面板保留 `≥1024px` 到窄窗口自适应折叠能力，不写死只能 `1920px` 才能看的绝对坐标布局。
3. **不再扩展原生 HTML 设置页**：所有新增设置 UI 只写在 `renderer/` 的 React 页面中，不再往 `desktop/public/settings/` 加复杂业务逻辑。
