# W06 父 run 续接设计（A13）

> 状态：**v0.1 草案（2026-11-10），待用户批准**。本文件是设计规格，不构成实施授权；批准前不改代码、不建迁移。
> 依据：`docs/27-AI对话增强分析与Codex桌面端对标设计.md` §11.3.2/§11.3.3/§11.3.4（T-AI27-S04/S06/S07/S08）、`docs/16-系统智能体设计.md` 第 6 节、`docs/31-执行台账.md` A13 行。
> 结论先行：**A13 应实现为"承接（adoption）"，不是"自动新建付费 run"**——27 §11.3.3 明确"没有对应活动父 run 时不得自动新建付费汇总运行"。docs/31 A13 行里"awaiting_confirmation→自动新 run"的措辞需要按本规格更正。

## 1. 问题与现状事实

### 1.1 要解决的问题

父 run 派发子任务后结束（`awaiting_confirmation`），子 run 完成时只回写委派行与组状态；父 run 不会恢复，子结果也没有任何路径进入下一次父级推理。用户必须自己再发一条消息，而新 run 对"上一轮委派组、子结果、剩余预算"一无所知——同一任务被当成新任务重新计费、重新授权、重复汇总。

## 2. 目标与非目标

**目标（本规格范围）**

1. 父 run 结束时把委派组置为"等待承接"，子结果持久化、可回查。
2. 用户下一次交互（或 goal 恢复）创建的 run **承接**同一组与剩余预算，拿到结构化子结果摘要，且只消费一次。
3. 任务级预算账本：预留→使用→结算，跨 run 不重复领取；超限显式拒绝。
4. 崩溃/重启后状态可恢复，不自动重放、不自动建 run。

**非目标**

- 不做"子结果到达即自动起新 run"（27 §11.3.3 明确禁止无活动父 run 的自动付费汇总）。
- 不改子任务"只能提案、不能执行卡片"的红线（27 §11.3.2）。
- 不在本期做父子并发（见 §14 分期与 §15 Q1）。
- 不改 goal/routine 既有预算语义，只定义与委派账本的衔接。

## 3. 术语

- **承接（adoption）**：新 run 在创建事务内认领一个委派组，成为其 `current_parent_run_id`，并一次性读取未消费的子结果。
- **任务（task）**：从一个根 run 起的同一目标，跨多个 run；预算账本以 `budget_scope_id` 标识。
- **预留（reservation）**：为保证子任务能跑完而提前占用的轮数/时长，未用部分在结算时释放。

## 4. 核心决策

| 决策 | 内容 | 理由 / 取舍 |
| --- | --- | --- |
| D1 承接而非自动 | 只有**用户触发的 run**（`message`/`continue`/`edit`）和 **goal resume** 可以承接；`routine`、后台定时、子 run 自身不得承接，也不得因"子任务完成"自动建 run | 27 §11.3.3 原文；避免无人值守时产生付费模型调用。代价：用户需再发一条消息或点"汇总" |
| D2 单活动 run 约束保持 | 承接 run 仅在组内**没有** `queued/running/cancelling` 子 run 时创建；否则返回 409 `delegation_children_running`（附组状态与可停止项） | 不放松 `agent_run_one_active`，避免父子同写一条消息序列；并发父子放到 Phase B（§14） |
| D3 组状态与 run 状态分离 | 组新增 `waiting_user`（父 run 结束且仍有未终态子任务/未承接结果）；`completed` 只表示"全部子任务终态"，不表示"已汇总"；承接与汇总用独立标记 | 27 §11.3.3"组状态与某次 run 状态分开"；避免把 completed 当成已读 |
| D4 结果只消费一次 | `results_consumed_at` + `consumed_by_run_id`；承接时在事务内 CAS，重复承接返回同一 run（幂等）或 409 `delegation_results_consumed` | T-AI27-S06"不重复汇总付费" |
| D5 预算一次领取、跨 run 继承 | 任务账本在根 run 首次派发时创建，额度 = 该任务总上限；承接 run **不新增**额度，只读剩余；提高额度必须显式用户确认 | 27 §11.3.3"新 run 续接同一目标不重复领取整笔预算" |
| D6 子消息不进主流 | 子 run 持久化为 `execution_origin='delegation'`；会话消息列表与父上下文默认排除子 run 消息，子结果只以摘要形式注入承接 run | 27 §11.3.1"主消息流只出现一次分工摘要和最终汇总"；现状 F8 是缺陷 |

## 5. 状态机

### 5.1 run

沿用现有状态，不新增状态。`awaiting_confirmation` 表示"本次 run 已结束、等待人工或下一次交互"，不表示"挂起可恢复的执行体"。

```
queued → running → completed
                 → awaiting_confirmation（提出卡片/等待人工）
                 → stopped / failed
```

新增两个**归属字段**（不是状态）：`root_run_id`、`parent_run_id`、`delegation_group_id`、`delegation_id`。

### 5.2 委派组

```
active ──父 run 结束且仍有未终态子任务/未承接结果──> waiting_user
active ──全部子任务终态──> completed
waiting_user ──承接 run 创建（子任务均已终态）──> completed（保留 adopted 标记）
waiting_user ──承接 run 创建（仍有子任务在跑）──> Phase B 才允许；Phase A 拒绝
active/waiting_user ──取消──> cancelled
active/waiting_user ──不可恢复失败──> failed
```

约束：`completed/cancelled/failed` 不可回到 `active`；承接只写标记，不复活组。

### 5.3 迁移触发点

| 事件 | 组状态变更 |
| --- | --- |
| 父 run 进入 `awaiting_confirmation`/`completed`/`failed`，且组仍有未终态子任务 | `active → waiting_user`（`parent_ended_at`、`parent_end_run_id`） |
| 子任务终态且全部终态 | `active/waiting_user → completed`（现有 `touchDelegationGroupOnChildDone` 扩展） |
| 承接 run 创建 | `adopted_run_id/adopted_at/adoption_count++`；组状态不变 |

- `agent_run` 的四个归属列用于"任一子结果可回溯到根任务"，同时支撑 T-AI27-S08 重启核对。

- Down 段必须带数据守卫：存在 `adoption_count>0` 或 `agent_task_budget` 行时拒绝回滚（沿用 00053/00065 的 `DO $$ ... RAISE EXCEPTION` 写法）。

## 7. 预算账本

### 7.1 池的创建

根 run 首次成功创建委派组时，在同一事务内创建 `agent_task_budget`：

| 项 | 默认值 | 依据 |
| --- | --- | --- |
| `rounds_limit` | `agentMaxRounds`（当前 12） | 27"沿用一次任务总模型轮数上限" |
| `seconds_limit` | 900s | 27 只给单子 3 分钟；任务级取 15 分钟（**开放问题 Q2**） |
| `tokens_limit` | goal 有则继承，否则 NULL（只记账不封顶） | 27"共享 token 池"；无来源时不做隐性限额 |

### 7.2 预留与结算

- 创组时预留 `Σ 子任务 4 轮` + 父汇总 `2 轮`；`seconds` 预留 `Σ 180s` + 父 120s。
- 预留前 `SELECT ... FOR UPDATE` 账本行；不满足则 429 `delegation_budget_exceeded`，不建组。
- 子 run 终态（`succeeded/failed/cancelled`）时结算：
  `rounds_used += 实际 rounds`，`rounds_reserved -= 该子预留`，`seconds_*` 同理，`tokens_used += prompt+completion`。
- 承接 run 结束时结算父预留的 2 轮/120s（实际超出则从剩余扣，不允许透支）。
- 取消组：未终态子任务按"已发生实际用量"结算，剩余预留全部释放。

### 7.3 不重复领取

- 承接 run **只读** `rounds_limit - rounds_used - rounds_reserved`，不写 `*_limit`。
- 提高额度只能走显式接口（建议 `PATCH /agent/delegation-groups/{id}/budget`，带 `expected_revision` 与 `confirm=true`），写审计事件 `delegation.budget_increased`。
- goal 恢复创建的 run 承接时，goal 自身的 `used_runs/used_tokens` 继续累加；两边通过 `budget_scope_id` 关联，用量面板按"父/子/合计"分项，避免重复计费（27 §11.3.3 末段）。

## 8. 承接流程

### 8.1 触发与前置

在 `agentStartRunTx`（`agent_propose.go:417`）内、插入 `agent_run` 之前执行：

1. `SELECT ... FROM agent_delegation_group WHERE conversation_id=$1 AND state IN ('active','waiting_user') AND adopted_run_id IS NULL ORDER BY updated_at DESC LIMIT 1 FOR UPDATE`。
2. 校验身份/工作区（组行已带 `user_id/workspace_id`）、`cancel_generation=0`。
3. Phase A：`SELECT count(*) FROM agent_delegation WHERE group_id=$1 AND state IN ('queued','running','cancelling')` 必须为 0，否则 409 `delegation_children_running`。
4. 读取子结果：`state IN ('succeeded','failed','cancelled','expired')`，按 `created_at` 排序，最多 4 条。

### 8.2 事务内动作

同一事务内：

1. 插入新 run（现有逻辑），写 `root_run_id`（沿用组的 root）、`parent_run_id=组.current_parent_run_id`、`delegation_group_id`。
2. 更新组：`adopted_run_id=新 run`、`adopted_at=now()`、`adoption_count=adoption_count+1`、`current_parent_run_id=新 run`、`revision=revision+1`。
3. 插入一条 `role='system_note'` 消息（`content` 为结构化摘要，≤6000 字符）：每条子任务含 `delegation_id/task/state/result_summary(≤500 字)/artifact_id/error_code`；明确标注"子结果未经父级复核，不得直接作为业务写入依据"。
4. **首次消费**：`results_consumed_at=now()`、`consumed_by_run_id=新 run`；若已消费则跳过注入并返回 409（幂等分支见 §8.3）。
5. 追加事件 `delegation.group_adopted`（含 group_id、run_id、子结果计数、预算快照）。

### 8.3 幂等

- 同一 `request_id` 重放：沿用现有 `agent_run.request_id` 幂等，命中旧 run 直接返回，不重复承接。
- 组已 `results_consumed_at != NULL`：新 run 仍可创建（普通对话），但不再注入子结果；返回的 run 事件带 `delegation_results_already_consumed=true`。
- 承接 run 创建失败（事务回滚）：组的 `adopted_run_id` 一并回滚，**不允许**出现"组指向不存在/失败 run 且结果已标记消费"的状态。

## 9. 崩溃与重启恢复

启动轮（挂 `RunJobs` 启动阶段）新增一次幂等 sweep：

1. 组 `active` 且全部子任务终态 → `completed`（补齐 F2 只在子完成时触发的缺口）。
2. 组 `waiting_user` 原样保留；**不创建任何 run**。
3. `adopted_run_id` 指向的 run 若 `failed/stopped` 且 `results_consumed_at` 为空 → 清空 `adopted_run_id/adopted_at`，写事件 `delegation.adoption_released`，允许下次承接。
4. 子 run `running` 但无 watcher（进程重启）：按现有 `interrupted` 语义置 `failed`，结算预留；不重放工具。
5. sweep 全程不加锁跨事务，逐组处理；失败只记录日志，下轮重试。

## 11. 权限与红线

- 承接 run 必须重新走完整鉴权（identity/workspace/账号快照），不得复用旧 run 的授权结论；子结果文本视为**不可信输入**，不提升为系统指令。
- 不新增任何"全部执行/自动执行"入口；卡片仍逐张由用户执行（D-117）。
- 不因承接自动扩大账号、模型、工具或预算范围；需要新权限时只生成待办/问题。
- `routine` 与后台调度不得承接、不得触发汇总 run。
- 子 run 的 `execution_origin='delegation'` 必须真实落库，供审计与消息过滤使用（修 F6）。

## 13. 迁移与回滚

- 迁移 `00100_agent_delegation_resume.sql`：仅加列/加表，不改历史行语义；`execution_origin` CHECK 扩展为前滚兼容（旧值仍合法）。
- 回填：历史组 `adoption_count=0`；`agent_task_budget` 不为历史组补建（无预算数据，宁缺不造）。
- Down：有 `adoption_count>0` 或 `agent_task_budget` 行时 `RAISE EXCEPTION` 拒绝，要求前滚修复。
- 部署顺序：先迁库，再启新二进制；旧二进制遇到新列不受影响（列均可空/有默认）。

## 14. 分期

- **Phase A（本规格）**：waiting_user、承接、预算账本、结果一次性消费、消息隔离、恢复 sweep、API/事件、测试。约 1 个开发批次。
- **Phase B（另立项）**：父子并发（放宽 `agent_run_one_active` 到"每会话 1 个非 delegation 活动 run + N 个 delegation run"）、子完整流按需读取 UI、跨 run 事件序列合并。Phase B 未做前，D2 的 409 是明确、可解释的行为。
