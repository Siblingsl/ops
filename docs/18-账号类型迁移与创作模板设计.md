## 2. 方案一：账号类型迁移（DEV-415）

### 2.1 决策（已登记为 D-123）

- 允许修改账号类型，**同平台内**迁移；跨平台（公众号 ↔ 小红书）不开放，仍需另建账号。
- 必须显式确认 `confirm_type_change: true`，不接受静默修改。
- 已有作品保持原类型不变，行为完全不变；新作品使用新类型。
- 迁移写入审计，含前后类型与受影响作品数。

### 2.2 接口契约

`PATCH /api/v1/accounts/{accountId}`（现有接口扩展）

请求体（在现有字段基础上新增两个）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `content_format` | string | 目标类型，必须命中 `formatMatrix[platform]` |
| `confirm_type_change` | bool | 为 true 才执行类型迁移；缺失或 false 时若 `content_format` 与现值不同，返回 409 |

响应 200（账号对象 + 迁移影响摘要）：

```json
{
  "id": "…", "platform": "wechat_mp", "content_format": "comic",
  "type_change": {
    "from": "long_article",
    "to": "comic",
    "works_kept": 7,
    "character_cards_kept": 2
  }
}
```

错误码：

| 场景 | 码 |
| --- | --- |
| 未确认 | 409 `confirm_required`，message 提示影响项 |
| 跨平台 | 422 `validation_failed`「跨平台需要新建账号」 |
| 类型不在矩阵 | 422 `validation_failed`（沿用现值字段级报错） |
| 非 owner | 403（`requireOwner` 已有） |

审计：`account_type_change`，detail 含 `from` / `to` / `works_kept` / `character_cards_kept`。

### 2.3 前端改动

`web/src/pages/settings/Accounts.tsx`：账号卡片增加「修改类型」入口（仅 owner 可见）→ 弹窗列出三项影响：

1. 已有 N 篇作品保持原类型，编辑/检查/推送行为不变；
2. 新建作品将使用新类型；
3. 漫画角色卡：转入 comic 立即可用；转出后仅当账号仍有漫画作品时可管理（沿用服务端兜底）。

`docs/06` 接口清单第 726 行需同步改写（现文案是「PATCH 修改 content_format 一律拒绝」）。

> **修订记录（A 项，实现时推翻初版设计）**：初版主张删掉 daily/plan 的「采用时校验类型 == 账号当前类型」，认为 `daily.go:466` 插入作品时写 `item.Format` 所以校验多余。**这是错的。** 那条校验保护的是一条不变式：**新建作品必须与账号当前类型一致**（D-048 第 5.5/5.6 节，`TestD048DailyTypeConstraint` 专门守它）。删掉它会让迁移后的账号通过「采用旧推荐」静默创建跨类型作品——把不变式从后门放倒。迁移只应让**已有**作品按作品级快照保持原类型，不放宽**新建**作品约束。因此：
> - daily/plan 采用时校验**保留**（代码注释已补明迁移场景下的拒绝理由）；
> - `contextpack` 的作品级类型**仍要修**（B/C 两项）——它解决的是相反的问题：给一篇「祖父级」旧类型作品起草时，提示词不该再报账号当前类型；
> - 回归测试 `TestD123AdoptDailyRecommendationAfterMigrate` 断言：迁移后旧类型推荐采用被拒、提示原因、且不产生跨类型作品。

### 2.7 看板口径（随迁移上线附带确认）

迁移后账号下作品类型可能混杂，`board` / 复盘结论若按账号聚合，会把漫画与长图文的表现混在一起比较。DEV-415 验收时确认：看板行已带 `content_format`（`work` 行自带），复盘报告按作品级输出即可，**不改聚合逻辑**；仅在前端看板标注类型列。

## 3. 方案二：创作模板（DEV-416）

### 3.1 一个结构性疏漏：交互顺序（修订记录）

初版把「账号类型」和「作品模板」当两层让用户分别选，这会把选择题从 **11 选 1 变成 11×N 选 1**，选择成本反而更高。修订后确认：

- **用户侧只有一个决策点**。新建作品时先选「模板」（教程文/观点文/攻略笔记…），类型由模板归属的类型**隐含确定**，默认不回退到让用户先选类型。
- 「直接选类型不选模板」保留为高级入口（模板 = 该类型的通用默认）。
- 模板少于 1 个的类型（首版大部分类型）仍显示为直接选类型。
- 智能体侧同理：`works__create` 由模板 id 创建，模型不需要同时决策两件事。

### 3.2 决策（拟登记为 D-124）

- **不开放自定义账号类型。** 每个类型必须有真实工作流支撑（D-048 第 9 节），自定义类型会制造空壳类型，把问题从“选不出类型”变成“选了类型不好用”。
- 弹性下沉到**模板层**：模板定义「大纲结构 + 提示词补充 + 段落数区间 + 语气」，只改表达与结构，不改工作流。
- 工作区级、可编辑、可另存；内置模板**每个类型不超过 2 个**，防止模板长成第二套封闭枚举。
- `type_note` 保留为纯备注，职责被模板吸收；提示文案改为「个别作品的补充说明，模板优先」。

### 3.3 数据模型

新表 `creation_template`（沿用 `prompt_template` 的 workspace 级 + 版本思路）：

```sql
CREATE TABLE creation_template (
    id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id   uuid NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    content_format text NOT NULL,                 -- 归属 11 类之一
    name           text NOT NULL,                 -- 教程文 / 观点文 / …
    builtin        boolean NOT NULL DEFAULT false,-- 内置只读，可另存为
    structure      jsonb NOT NULL DEFAULT '[]',   -- [{heading, key_point, role}]
    prompt_addon   text NOT NULL DEFAULT '',      -- 注入大纲/起草提示词的补充要求
    section_min    int  NOT NULL DEFAULT 0,
    section_max    int  NOT NULL DEFAULT 0,       -- 0 表示不限制
    tone           text NOT NULL DEFAULT '',
    updated_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON creation_template (workspace_id, content_format);
```

### 3.4 接口契约

| 方法 | 路径 | 用途 | 备注 |
| --- | --- | --- | --- |
| GET | `/creation-templates?content_format=` | 列出该类型模板（内置 + 工作区） | 内置排在前面并标 `builtin` |
| POST | `/creation-templates` | 新建工作区模板 | 校验结构条数 1–20 |
| PUT | `/creation-templates/{id}` | 编辑 | 内置模板返回 422「内置模板不可修改，可另存为」 |
| DELETE | `/creation-templates/{id}` | 删除 | 仅工作区模板；引用中的作品保留快照 |

模板进入作品的入口：新建作品向导选择 + 编辑器顶部可切换（切换只影响后续生成，不改已写内容）。作品是否记录所用模板：记录 `template_id` 到 `work` 表（可空），便于复盘「哪种模板效果好」。

### 3.5 AI 注入契约

- `POST /works/{id}/outline/generate`：请求体可选 `template_id`；服务端把模板的 `structure` / `prompt_addon` / `tone` / 段落区间写进用户提示，要求模型按结构输出；输出条数超出区间时**软提示**（不阻断，提示用户可增删）。
- `POST /sections/{id}/draft`：注入 `prompt_addon` 与 `tone`，`SkipStyle` 不变，风格样本仍生效。
- 模板与 `type_note` 同时存在时都注入，提示词里明确分工：模板管结构，type_note 管这篇的个别补充。
