## 0 使用说明与事实基线

### 0.1 四态口径（沿用 AGENTS.md 与 docs/31:9）

| 状态 | 含义 | 本文判据 |
|---|---|---|
| 需求已设计 | 设计文档/决策已登记 | 文档条目存在，带文件:行号 |
| 代码已实现 | 源码中存在可调用实现 | 源码路径 + 行号 + 关键函数/字段；仅注释或表结构不算 |
| 验证已通过 | 有实际命令输出 | 区分「本机/mock」「真实模型」「真实平台」「真实设备」 |

### 10.2 P0：`mcp:oauth-status` 的状态查询永远返回 `unauthorized`

**三段代码拼起来的确定性契约错误【实证】**：

```ts
// desktop/src/main.ts:1143-1147 —— 主进程返回「包了一层 status」
ipcHandle('mcp:oauth-status', async (event, raw) => {
  requireComputerCaller(event);
  const input = parseOAuthInput(raw);
  const client = mcpOAuthClientOf(input.connectionId, input.serverUrl, input.clientId, input.scopes);
  return { ok: true as const, status: client.statusView() };
});
```
```ts
// desktop/src/mcp-oauth.ts:467 —— statusView() 返回顶层三键
statusView(): { state: OAuthState; expires_at: string | null; has_refresh: boolean }
```
```ts
// desktop/src/business-ui-preload.ts:268-276 —— preload 要求 raw 本身必须是三键白名单
if (Object.keys(value).sort().join(',') !== 'expires_at,has_refresh,state') return null;
// :425 直接把 invoke 结果交给解析器，没有取 .status
const result = parseMcpOAuthStatus(await ipcRenderer.invoke('mcp:oauth-status', input));
// :427 解析失败 → 恒定降级
return result ?? { state: 'unauthorized', expires_at: null, has_refresh: false };
```

**判定**：主进程返回 `{ok:true, status:{...}}` 有 2 个顶层键，preload 要求恰好 3 个键 → 解析恒为 `null` → UI 永远显示 `unauthorized`。对照 `mcp:oauth-start` 返回 `{ok,state,reason}` 与 `parseMcpOAuthStartResult`（`:279-282`）形状一致，说明**只有 status 通道形状错位**。

**影响边界（不得夸大）【推断】**：
- 受影响的是**状态展示**：已授权连接会被显示成未授权，用户可能重复走授权流程。
- **不**影响令牌存储、刷新与注入——`mcp:oauth-start` / `revoke`、`mcp:validate` 的 `oauth` 注入走的是另一条路径（`main.ts:1080-1086`）。
- **不**构成令牌泄漏：preload 的三键白名单正是「令牌零泄漏」断言，应保留。
- 【未核实】未做真实窗口 UI 运行时复现；静态代码链已足以判定形状不匹配，但 DT-01 仍须先补一条失败用例。

**修法选择**：推荐 **方案 A**——把主进程返回值改为 `client.statusView()` 顶层展开（保持 preload 白名单与 `mcp:oauth-start` 风格一致），不动 preload。**不推荐方案 B**（preload 解包 `.status` 并放宽白名单）：那会削弱令牌零泄漏断言。若 `ok` 字段对其它调用方有用，须先 `grep` 全仓确认无消费者再决定，不要臆测。

### 10.3 安全边界：诊断 IPC 来源校验与输入侧 schema

**包装器不自带校验【实证】**：`main.ts:3074-3078` 的 `ipcHandle()` 只是 `ipcMain.handle(channel, (event, ...args) => handler(event, ...args))` 的薄封装，**没有**统一的来源窗口校验。敏感通道靠各 handler 自行调用守卫。

**已有的正确范例【实证，应推广而非重写】**：`requireComputerCaller`（`main.ts:971-978`）与 `requireRealtimeCaller`（`:892-899`）同时校验 `event.sender === businessWindow.webContents`、`senderFrame === mainFrame`、以及 `isBusinessUrl()` 对 frame URL 与 `getURL()` 的双重判断。

**缺口 1：诊断 IPC 无来源校验【实证】**

```ts
// desktop/src/browser-bridge.ts:757-765（registerIpc()）

ipcMain.handle('ops-bridge-diag:confirm-pairing', () => ...);
```
