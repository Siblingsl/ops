## 0. 结论

1. **主链路功能已经完整，短板不在"缺功能"。** 04 文档中的 P0/P1 需求前后端基本都已落地；没做的几项（微信第三方平台、小红书官方 SDK、认证账号的数据接口）都卡在外部资质，不是代码问题。
2. **真正的风险集中在三处：**
   - **安全**：线上只有 HTTP，登录密码、会话和模型 API Key 都在明文传输（OPT-01）。
   - **接入真实模型后的稳定性**：模型调用占着数据库连接和锁（OPT-02）、连接池全默认（OPT-03）、流式 AI 不受并发上限约束（OPT-04）。几个人同时用、模型稍慢，就可能出现全站卡住或随机失败。
   - **长期运行**：AI 调用记录、操作日志、版本只增不删（OPT-11），容器无资源上限和日志轮转（OPT-16），出了问题没有请求 ID 可查（OPT-15）。
3. **最划算的一项是静态资源压缩与缓存（OPT-05）。** 实测线上主脚本未压缩（399KB），开启 gzip 后约 124KB，半天以内就能完成，首次打开和每次回访都能明显变快。
4. **日常使用最缺的两个功能**：复制作品（OPT-20）和把已发布的旧文导入成可编辑作品（OPT-21）。
5. **AI "不够聪明"的主要原因不是模型，而是没用好手上已有的信息（第三轮，第 6.1 节）。** 选中的素材会被按字数丢掉（OPT-42）；改写扩写不带素材（OPT-43）；拟标题不看风格、不避开旧标题、不参考本号高表现特征（OPT-44）；大纲读不到用户确认过的正文记忆（OPT-46）；格式出错的重试不告诉模型错在哪（OPT-45）。这 5 项都是半天级改动，接入真实模型之前做完，效果最明显。
6. **动线上有一条确定的死链和几处多余步骤（第 6.2 节）。** 派生漫画会跳回首页（OPT-53）；第二天打开作品要重新找位置（OPT-54）；正文写完后工作台的"下一步"就断了（OPT-47）。
7. **编辑器有两个会让人不信任的问题（第 6.3 节）**：一个人写也可能弹冲突（OPT-63）；关掉冲突对话框后修改可能丢失（OPT-64）。另外中文输入法按回车选词会直接触发提交（OPT-65），日常必然碰到。
8. **建议顺序**：先用约一周做完 4 个 P0 和几项小成本 P1（第 10 节第一批），再处理数据一致性、编辑器可靠性和 AI 上下文，P2 按需。

- **方法**：后端、前端、产品流程与部署、功能缺失、性能与资源、正确性与数据一致性，分 6 路检查代码；关键结论回到代码逐条复核；HTTPS、压缩、缓存头对线上站点实际请求验证。

## 3. P0 必须解决

### OPT-01 线上没有 HTTPS

- **问题**：站点只能走 HTTP。登录密码、会话 Cookie、模型配置页填写的供应商 API Key 都以明文经过网络；Cookie 未设 Secure，没有 HSTS。
- **证据**：线上实测 `http://ops.88813888.xyz/` 返回 200、不跳转、无 `Strict-Transport-Security`；443 端口可连接但 TLS 握手失败。`deploy/nginx-ops.conf:36-62` 的 443 配置整段注释；`.env.example` 中 `OPS_COOKIE_SECURE` 默认 0。线上为 nginx/1.21.5，实际配置可能与仓库模板不同，需上机确认。
- **方案**：服务器上用 certbot 签发证书并启用 443；80 端口 301 跳转到 https；加 HSTS（先 `max-age=300` 验证，再拉长）；`.env` 设 `OPS_COOKIE_SECURE=1` 后重启；最终 nginx 配置回写仓库模板。
- **收益**：消除当前最大的真实安全风险；也是录入真实模型密钥、真实公众号凭证的前提。
- **验收**：`curl -I http://…` 返回 301 指向 https；`https://…/healthz` 返回 ok；登录响应的 `Set-Cookie` 含 `Secure`；SSL Labs 评级 ≥ A。

### OPT-02 每日推荐在事务和锁里等模型返回

- **问题**：`generateDaily` 先开事务、拿 advisory 锁，再在事务里调用模型（最长到 HTTP 客户端 5 分钟超时），最后才写入提交。期间这条连接处于"事务中空闲"状态。
- **证据**：复核时 `server/internal/app/daily.go:179-218`：`Begin` → `pg_advisory_xact_lock` → `dailyAI(...)` → `INSERT` → `Commit`；同文件 `dailyAction:306-350` 的单条“换一个”也在行锁事务中调用 `dailyAI`，属于本项“同时排查”的范围。`accounts.go:531-572` 的 token 刷新行锁则是 06 文档 5.3 节明确规定的防重复机制，本项保留。
- **方案**：拆成三段：①短事务内检查"今天是否已有、重生成次数"；②事务外调用模型；③短事务写入，写前按版本号复核（被抢先则返回已有结果）。同时排查其它"事务内调用模型或外部 HTTP"的位置。
- **收益**：模型变慢时，不会因为几次推荐生成占满数据库连接导致全站卡住。
- **验收**：模拟模型延迟 30 秒期间，`pg_stat_activity` 中 `idle in transaction` 连接数为 0；并发请求工作台接口 p95 劣化不超过 20%；新增测试覆盖"并发两次生成只产生一个版本"。

### OPT-03 数据库连接池全默认

- **问题**：没有显式最大连接数、连接寿命、`statement_timeout`、`idle_in_transaction_session_timeout`。一处慢查询或未提交事务就可能耗尽连接池，表现为所有页面一起转圈。pgx 默认上限为 max(4, CPU 核数)，2 核机器只有 4 条。
- **证据**：`server/internal/db/db.go:34-43` 直接 `pgxpool.New(ctx, url)`；`deploy/docker-compose.prod.yml:23` 的连接串无池参数。
- **方案**：改用 `pgxpool.ParseConfig`，显式设置 `MaxConns`（建议 20，可由环境变量覆盖）、`MaxConnIdleTime`、`MaxConnLifetime`；连接参数设 `statement_timeout=30s`、`idle_in_transaction_session_timeout=60s`，后台长任务单独放宽。
- **收益**：把"一个慢操作拖垮全站"变成"单个请求超时报错"。
- **验收**：启动日志打印池参数；人为执行 `pg_sleep(40)` 的请求在 30 秒被取消并返回中文错误；期间 `/healthz` 仍返回 200。

### OPT-04 流式 AI 不受工作区并发上限约束

- **问题**：后台任务会进入工作区信号量排队，但起草、改写、副驾驶等流式接口直接开协程调用模型。多人或多标签页同时起草会同时打到供应商，触发 429，用户看到的是随机失败。
- **证据**：`server/internal/app/aijobs.go:134-141` 只有 `startBackgroundJob` 获取 `workspaceSem`；`aicore.go:409-445` 的 `streamAIJob` 协程直接调用 `runAI`。
- **方案**：流式任务也获取同一信号量（或独立流式配额，默认 `AIWorkers×2`）；等待时推送 `stage=queued`，前端显示"排队中"；等待超过 60 秒返回可重试错误。
- **收益**：接真实模型后最常见的故障（供应商限流）变成可预期的排队，成本也可控。
- **验收**：`AIWorkers=1` 时并发发起两次起草，第二个先收到 `queued`、在第一个完成后才开始；模拟模型记录的同时在途请求数不超过上限。

## 4. P1 重点优化

### OPT-05 静态资源未压缩、无长期缓存头

- **问题**：前端脚本和 JSON 都以原始大小传输；带哈希的静态文件没有长期缓存头，回访时仍要重新校验或下载。
- **证据**：线上实测 `assets/index-C6ZBMblu.js` 带 `Accept-Encoding: gzip, br` 请求，返回 `Content-Length: 399437`、无 `Content-Encoding`、无 `Cache-Control`。`deploy/nginx-ops.conf` 无 gzip 配置；`server.go:456-471` 的 `spaHandler` 是裸 `FileServer`；nginx 对所有路径 `proxy_buffering off`（`nginx-ops.conf:28-30`）。
- **方案**：nginx 开启 gzip（`application/javascript text/css application/json image/svg+xml`，`gzip_min_length 1024`）；`/assets/` 返回 `Cache-Control: public, max-age=31536000, immutable`，`index.html` 返回 `no-cache`；`proxy_buffering off` 只保留给流式接口（SSE 路径）。Go 侧可同时加压缩中间件作为兜底（流式响应除外）。
- **收益**：首次打开传输量约降到三分之一（主包约 124KB），回访静态资源零下载。
- **验收**：`/assets/*.js` 响应含 `Content-Encoding: gzip` 和 `immutable`；大于 1KB 的 JSON 响应被压缩；SSE 起草仍逐字显示。

### OPT-06 写入公众号草稿箱没有并发保护

- **问题**：同一作品被连点两次，或两位成员同时点"写入草稿箱"，两个请求都会通过检查并各自调用微信接口，草稿箱出现两份，当日写入次数也被重复计算。
- **证据**：`server/internal/app/publish.go:149-192`：检查修订号、统计当日次数后直接 `INSERT INTO push_record … 'running'`，作品行未加锁，也没有"已有进行中记录"的判断。
- **方案**：写入前在事务内 `SELECT … FROM work WHERE id=$1 FOR UPDATE` 并检查是否存在 `status='running'` 且在 10 分钟内的 `push_record`，存在则返回"正在写入，请稍候"；或用部分唯一索引 `(work_id) WHERE status='running'` 兜底。前端按钮在请求期间禁用。
- **收益**：避免草稿箱重复和推送计数虚高；也降低被平台视为频繁写入的风险。
- **验收**：并发两次写入同一作品，只产生一个新的 `media_id`，第二个请求返回明确提示；新增 Go 测试。

### OPT-07 AI 写回、恢复历史、调整顺序、改标题不校验修订号

- **问题**：手动编辑保存会校验 `base_revision`，但 AI 起草/改写写回、恢复段落历史、确认大纲生成段落、调整段落顺序、修改标题摘要都直接覆盖。协作者在 AI 生成期间改了同一段，结果会被 AI 静默覆盖（历史里还能找到，但当事人不知道）。
- **证据**：受保护的 `writing.go:332-343`；不受保护的 `saveAIContent`（`writing.go:478-483`，只 `FOR UPDATE` 不比修订号）、`restoreSectionRevision`（`editorai.go:198`）、`reorderSections`（`writing.go:301`）、`updateWork`（`works.go:451-458`）。
- **方案**：AI 请求开始时记录段落修订号，写回时若修订号已变化，不覆盖，改为返回"这段在生成期间被修改过"，前端提供"替换 / 保留当前 / 对比"三选一；恢复、排序、改标题带上 `base_revision`，冲突时复用现有冲突对话框。
- **收益**：多人协作时不再出现"我的修改不见了"。
- **验收**：模拟"开始起草 → 另一会话修改同段 → 起草完成"，结果不覆盖且前端出现选择；恢复/排序/改标题在修订号过期时返回 `version_conflict`。

### OPT-08 编辑器选中文字或自动保存时所有段落重渲染

- **问题**：`SectionBlock` 没有 memo；父组件每次渲染都为每段新建在线成员数组和 `onMove/onRemove` 闭包。选区变化、保存计数（开始 +1、结束 −1）、20 秒一次的在线状态，都会让整篇所有 TipTap 段落重渲染；同时每次渲染都对全文跑一遍待核实标记的正则。
- **证据**：`Editor.tsx:962-964`（`onActive` 内 `setSelection`）、`944-945`（`setSave` 每次保存两次）、`1266-1268`（每段内联数组与闭包）、`1028`（`pendingAll` 全文 `matchAll`）；`section-block.tsx:106` 未 memo。实际卡顿程度未测量。
- **方案**：`memo(SectionBlock)`；在线成员按段预先分组并缓存；`onMove/onRemove` 改为接收 id 的稳定回调；选区改存 ref，只让侧栏订阅；保存状态移到独立小组件；待核实标记按段 `useMemo`。
- **收益**：15～30 段长文输入和选中更跟手，低配笔记本收益最大。
- **验收**：React Profiler 在 20 段作品中，选中文字或自动保存时只有当前段重渲染；单次提交耗时 < 16ms。

### OPT-09 工作台单次请求 11～14 条 SQL；顶栏为取用量也调用工作台接口

- **问题**：工作台接口串行执行账号、方案准备、状态分组、待办、选题计数、今日推送数、今日用量、路由检查、样本计数、画像、限额等十余条查询；顶栏只为显示"今日用量"也在每个页面调用这个接口。
- **证据**：`review.go:548-641`（工作台处理链）；`web/src/layout/Shell.tsx:667-671`（顶栏 `queryKey: ['dashboard', acc?.id]` 只取 `tokens_today`）。
- **方案**：今日用量改从轻量接口获取（如 `/ai/status` 或 `/auth/me` 附带）；工作台把计数类查询合并为一条 CTE，"准备方案"移到首次进入运营页时执行。
- **收益**：每次切页少一组重查询，工作台首屏更快。
- **验收**：非工作台页面不再请求 `/dashboard`；工作台接口热路径 ≤ 5 条查询，p95 < 150ms。

### OPT-10 素材列表一次返回 500 条全文，编辑器打开即加载

- **问题**：素材列表接口带完整正文返回最多 500 条；编辑器打开时就请求整份素材列表，素材越多，打开作品越慢。
- **证据**：`server/internal/app/memory.go:215`（`materialCols` 含 `m.content`）、`:261`（`LIMIT 500`）；`web/src/pages/work/Editor.tsx:65-68` 打开即请求 `/materials?account_id=…`。
- **方案**：列表接口只返回前 120 字摘要和元数据，打开详情或插入时再取全文；编辑器的素材请求延后到侧栏"素材"标签首次打开时。
- **收益**：素材多的账号打开作品明显更快、更省流量。
- **验收**：200 条素材时列表 JSON < 100KB；打开作品时不请求素材全文。

### OPT-11 ai_call、audit_log、work_version 只增不删

- **问题**：每次 AI 调用、每条操作日志、每个手动版本都永久保留。表和索引持续膨胀，备份越来越大、越来越慢，相关查询逐渐变慢。
- **证据**：全仓库只有测试代码删除这三张表的数据；对比 `hot_item/crawl_run`（`crawl.go:243-248`）和 `section_revision`（`writing.go:464`，保留 30 条）都有清理。
- **方案**：先在 90 文档登记保留期（建议：ai_call 明细 180 天、按月汇总永久；audit_log 365 天；work_version 每篇保留最近 50 个，加所有发布、检查节点版本），再在 `RunJobs` 加每日清理，分批删除避免长时间锁表。合规上需要保留的 AI 生成披露信息先确认再删。
- **收益**：长期运行无需人工清库；备份时间与磁盘占用保持平稳。
- **验收**：清理任务有测试；一年量级的模拟数据下三张表行数在上限内；每批删除 ≤ 5000 行、单批 < 1 秒。

### OPT-12 缺索引

- **问题**：①热点入库时在全局锁内对 `hot_item` 做 `similarity(title_norm)`，没有 trigram 索引，数据越多采集越慢；②作品"动态"按 `target_id` 查操作日志，只有 `created_at` 索引；③作品列表、选题列表按 `updated_at` 排序，只有 `account_id` 索引。
- **证据**：`crawl.go:176-196`；`00012_v4_hot.sql:43/48`（`title_norm` 无索引）；`collab.go:278`、`00001_init.sql:380`；`00001_init.sql:196`（`work_account` 只含 `account_id`）。2026-10-12 复核：`crawl.go:195-196`、`collab.go:278-279`、`works.go:379` 缺对应索引仍成立；`topics.go:70` 实际按 `pinned_at DESC NULLS LAST, created_at DESC` 排序，应按此建立选题联合索引，不改变为更新时间排序。
- **方案**：新迁移：`hot_item USING gin (title_norm gin_trgm_ops)`，查询改用 `%` 运算符配合 `set_limit(0.6)` 以走索引；`audit_log (target_id, created_at DESC)`；`work (account_id, updated_at DESC) WHERE deleted_at IS NULL`，`topic` 同理。
- **收益**：热点采集耗时与数据量脱钩；动态侧栏、作品与选题列表随数据增长保持稳定。
- **验收**：EXPLAIN 显示走索引；1 万条热点下单次入库 200 条 < 2 秒；作品动态接口 p95 < 100ms。

### OPT-13 工作台接口失败时一直显示加载中

- **问题**：工作台主查询出错时没有错误分支，用户只看到一直转圈，以为系统卡死。
- **证据**：复核时 `web/src/pages/Dashboard.tsx:259`：`if (!acc || isLoading || !data) return <PageLoading />`，未处理 `isError`；同类写法还见 `Profile.tsx:794`、`settings/Usage.tsx:44`、`settings/Quality.tsx:152`、`work/Push.tsx:66`。`main.tsx:17` 全局重试 2 次，首次失败时尚未进入终态错误，需要及时展示查询的首次失败原因。
- **方案**：增加错误分支，显示原因与"重试"按钮；抽出统一的加载/空/错误三态组件，排查其它页面"无数据即加载中"的写法。
- **收益**：故障时用户知道发生了什么，能自己恢复。
- **验收**：模拟 `/dashboard` 返回 500，1 秒内出现错误提示与重试按钮；E2E 增加一条用例。

### OPT-14 前端请求没有超时，nginx 错误页显示为"请求失败"

- **问题**：`fetch` 没有默认超时，网络半断时请求会一直挂着；nginx 返回 413（上传过大）、429、502/504（后端重启或超时）时是 HTML 页面，前端只能显示"请求失败（502）"。
- **证据**：`web/src/lib/api.ts:50-72`（无 `AbortController` 超时）；`api.ts:33-41`（非 JSON 一律"请求失败"）。复核补充：`server/internal/app/assets.go:154-157` 提前限制请求体，30MB 直传时本地 Vite 代理可发生 `ECONNRESET`，丢失后端大小错误；前端共享上传入口需按既有单文件 20MB 上限先检查。
- **方案**：普通请求默认 30 秒超时（流式与上传单独设置）；按状态码给出明确提示："文件太大，最大 20MB""服务正在重启，请稍后重试""请求太频繁"；幂等的 GET 遇到 502/503/504 自动重试一次。
- **收益**：部署重启、弱网时用户得到可理解的提示，而不是卡住或看不懂的报错。
- **验收**：模拟后端停止时，页面 30 秒内给出"服务暂不可用"提示；上传 30MB 文件显示大小限制提示。

### OPT-15 没有请求 ID、访问日志和慢请求记录

- **问题**：中间件只有 `RealIP` 和 `Recoverer`。用户反馈"刚才起草失败了"，日志里无法定位到具体请求；慢接口没有记录。HTTP 服务只设置了 `ReadHeaderTimeout`。
- **证据**：`server.go:94-97`；`cmd/ops/main.go:121`。登录失败锁定已有（`auth.go:207/222`），不需要另加登录限流。
- **方案**：加 chi `RequestID` 和 slog 访问日志（方法、路由模板、状态、耗时、工作区），超过 1 秒记警告；响应头回传 `X-Request-ID`，前端错误提示附短 ID；设置 `IdleTimeout`，非流式路由加读超时。
- **收益**：定位线上问题从"猜"变成"按 ID 查"，为接真实模型后的调试打基础。
- **验收**：每条请求日志含 request_id 与耗时；错误提示显示可复制的短 ID，能在服务器日志中检索到对应记录。

### OPT-16 生产容器无资源上限、无日志轮转

- **问题**：应用或数据库失控时会吃满整台服务器内存；Docker 日志无限增长，最终写满磁盘，数据库也无法写入。
- **证据**：`deploy/docker-compose.prod.yml` 无 `mem_limit`、`cpus`、`logging` 配置。
- **方案**：为 app、postgres 设置内存与 CPU 上限；`logging` 使用 `json-file`，`max-size: 10m`、`max-file: 3`。
- **收益**：消除"磁盘写满、内存打满导致全站宕机"的长期风险。
- **验收**：`docker inspect` 可见限制；持续写日志压测后单容器日志总量 ≤ 30MB。

### OPT-17 端到端测试不在 CI，未覆盖公众号主路径；两个锁文件并存

- **问题**：6 条 Playwright 用例只能手动运行，且偏小红书；"公众号写入草稿箱""回填已发布、录入数据"没有浏览器级回归。DEV-UX02 的重复按钮问题就是靠手动跑 E2E 才发现的。`web/` 下同时存在 `package-lock.json` 和 `pnpm-lock.yaml`，CI 用 npm、本地用 pnpm，依赖版本可能不一致。
- **证据**：`.github/workflows/ci.yml` 只有 `go test` 与前端类型检查、构建；`web/e2e/smoke.spec.ts` 共 6 条。
- **方案**：CI 增加 E2E 任务（Postgres 服务 + 模拟模型与模拟微信），失败时上传 trace；新增两条用例：公众号"起草 → 检查 → 写入草稿箱"，"回填已发布 → 录入节点数据"；统一为 pnpm，删除 npm 锁文件。
- **收益**：前端改动有自动兜底，主链路回归不依赖人工。
- **验收**：每次推送 main，CI 跑 8 条 E2E 全部通过；仓库只保留一个锁文件。

### OPT-18 设置菜单平铺 16 项

- **问题**：个人创作者日常只用"平台账号""模型配置""成员"，却要在 16 个平铺入口中查找；质量看板、提示词模板、热点来源等对新用户是噪音。
- **证据**：`web/src/layout/Shell.tsx:42-57`。
- **方案**：分为"常用"（平台账号与凭证、模型配置、成员与邀请、偏好设置）和"高级"（其余，默认折叠，记住展开状态）；仅管理员可见的继续隐藏；命令面板可搜到全部设置。所有原有路由不变。
- **收益**：降低学习成本，新用户第一次就能找到该配的地方。
- **验收**：设置菜单默认可见入口 ≤ 5 个；原有路由均可访问。

### OPT-19 模型供应商故障时没有熔断

- **问题**：已有首字 15 秒超时和一次备用模型切换，但供应商整体不可用时，每个操作都要先等到失败；没有退避，也没有"暂时不可用"的快速失败。
- **证据**：`aicore.go:171-177`、`187-211`、`284-286`。
- **方案**：按供应商维护滑动窗口失败计数：1 分钟内连续 3 次失败即熔断 60 秒，期间直接走备用模型或快速返回"供应商暂不可用，约 N 秒后恢复"；模型配置页显示供应商当前状态。
- **收益**：供应商抖动时，用户 1 秒内得到明确反馈，而不是每次等十几秒。
- **验收**：模拟供应商持续返回 500，第 4 次起请求在 1 秒内返回明确提示；60 秒后自动探测恢复；有单元测试。

### OPT-20 不能复制作品

- **问题**：系列文章、固定栏目每次都要从头新建；现有"派生"只能派生到另一平台类型，同类型作品无法复制。
- **证据**：`server.go` 无作品复制路由（只有 `/materials/duplicates` 查重）；作品列表与编辑器无复制入口。
- **方案**：`POST /works/{id}/duplicate`（单个作品、单次操作）：复制标题（加"副本"）、观点、大纲和段落正文、图片引用，状态重置为草稿，不复制检查结果、推送记录和数据；在作品列表与编辑器"更多"中提供"复制为新草稿"。
- **收益**：固定栏目、系列内容的起稿时间从几分钟降到几秒。
- **验收**：复制后的作品可独立编辑，原作品不受影响；不复制推送与数据记录；有 Go 测试。

### OPT-21 不能把已发布旧文导入为可编辑作品

- **问题**：已有的旧文只能作为风格样本或素材（首次推荐路径的"旧文建档"），不能变成可再编辑、再派生的作品；想基于一篇爆款写续篇或改写成小红书，需要手动复制粘贴分段。
- **证据**：无导入作品的路由；风格样本在 `Profile.tsx`，参考文章在 `references.go`。
- **方案**：先做"粘贴导入"：粘贴正文（Markdown 或从公众号复制的富文本）→ 预览按小标题自动分段 → 用户确认后生成一个状态为"已发布"的作品（可填发布日期，用于数据回填）。URL 导入只允许用户主动提供的单个公开链接，并按 11 文档的限额读取，不使用登录态。一次只导入一篇。
- **收益**：旧内容资产可以继续派生、复盘，首次使用就能看到自己的历史作品。
- **验收**：粘贴一篇 3000 字公众号文章，10 秒内生成分段正确的作品；导入后可派生为小红书；不提供多篇一次导入。

### OPT-22 标签页在后台时仍持续轮询

- **问题**：编辑器在线状态每 20 秒、批注每 60 秒、通知每 30～120 秒轮询，通知还保持推送连接；切到别的标签页后照常进行，多开几个作品时尤其明显。
- **证据**：`WorkLayout.tsx:254-260`、`editor-sidebar.tsx:49`、`notifications.tsx:31-65`；`web/src` 中没有任何 `visibilityState` 或 `document.hidden` 判断。
- **方案**：页面隐藏时暂停轮询并关闭推送连接，重新可见时立即刷新一次。React Query 的 `refetchIntervalInBackground` 默认已为 false，主要处理手写的 `setInterval` 和 `EventSource`。
- **验收**：标签页隐藏 5 分钟内，在线状态与批注请求为 0；切回后 1 秒内刷新。

### OPT-23 React Query 无默认 staleTime

- **证据**：`web/src/main.tsx:12-18` 只设置了 `refetchOnWindowFocus: false` 和重试规则。
- **方案**：全局 `staleTime: 30_000`；通知、AI 任务、在线状态保留各自设置；写操作后按前缀失效（现有做法）。
- **验收**：30 秒内从作品返回工作台，未变化的查询不发请求。

### OPT-24 主包与编辑器包体积偏大

- **证据**：本地构建 `index` 399KB（gzip 124KB），`section-editor` 529KB（gzip 184KB）；`App.tsx` 同步引入 `Shell`，`Shell` 同步引入命令面板与通知面板。
- **方案**：先完成 OPT-05（压缩带来的收益最大）；再把命令面板、通知面板改为按需加载；用打包分析工具确认 TipTap 扩展是否有未用部分后再拆，不盲目拆分。
- **验收**：主包 gzip ≤ 90KB；Fast 3G 模拟下工作台首屏可交互时间缩短 ≥ 25%。

### OPT-25 窄屏编辑时用不了侧栏工具

- **证据**：`Editor.tsx` 侧栏容器为 `xl:block`，窄屏没有替代入口。
- **方案**：宽度小于 xl 时侧栏改为右侧抽屉，工具栏按钮或 Ctrl+J 打开，覆盖正文而不挤压。
- **验收**：1024px 与 390px 宽度下可打开全部 7 个侧栏标签并正常操作。

### OPT-26 重新起草前未先保存最后 1.2 秒的修改（潜在风险）

- **证据**：`section-block.tsx:299` 只 `clearTimeout`；对比 `edit()` 调用前 `await flush()`。
- **方案**：`draft()` 确认后先 `await flush()`，再发起流式请求。
- **验收**：输入文字后立即重新起草，段落历史中能看到刚输入的版本。

### OPT-27 会话与 CSRF 过期没有预告

- **证据**：`auth.go:17-19`（会话 7 天）；`httpx.go:44`（CSRF 失败提示刷新）。
- **方案**：页面重新获得焦点时静默刷新 CSRF；会话剩余不足 1 天时顶部提示续期。
- **验收**：标签页闲置 8 小时后直接保存成功，不出现"页面已过期"。

### OPT-28 作品详情与推送预览载荷偏重；正则每次编译

- **证据**：`works.go:28-38` 的 `sectionCols` 总是查询 `ai_raw_md`（不返回给前端）；获取作品时先 `workMetaFromPath` 再 `loadWork`，作品行查两次；`publish.go:40-43` 推送预览加载整篇作品；`plaintext.go:36` 在循环内 `regexp.MustCompile`。
- **方案**：详情查询去掉 `ai_raw_md`，复用已查到的作品行；推送预览只查所需列；正则提到包级变量。
- **验收**：获取作品的查询数 ≤ 5；推送预览不读取正文。

### OPT-29 作品列表子查询偏多；选题列表无分页、打分时逐条检索素材

- **证据**：`works.go:358-379` 每行 5 个相关子查询、`LIMIT 300`；`topics.go:70` 无 `LIMIT`；`topics.go:106-112` 在循环中对每个选题调用 `retrieveMaterials`。
- **方案**：作品列表改用 `LEFT JOIN LATERAL` 或冗余字数、段落数；选题列表分页（默认 50）；打分改为一次检索后批量计算。
- **验收**：300 篇作品时列表 p95 < 100ms；打分请求只做一次素材扫描。

### OPT-30 图片无缩略图；超大尺寸图片先完整解码

- **证据**：`assets.go:248-250` 始终返回原图，`Images.tsx:68`、`Works.tsx:164` 列表直接用原图；`assets.go:112-118` 先 `image.Decode` 再判断尺寸。
- **方案**：上传时生成 256/512 宽缩略图，列表使用缩略图；解码前先 `image.DecodeConfig`，像素数超过上限直接拒绝。
- **验收**：图片库单图平均传输 ≤ 50KB；上传 20000×20000 PNG 被拒绝且内存增长 < 50MB。

### OPT-31 每日任务在当天 3 点后全程停机时不会补跑（潜在风险）

- **证据**：`jobs.go:59-65` 每 10 分钟检查一次，北京时间 3 点到 24 点之间按 `markOnce` 的日期键执行一次；只有当天 3 点后一直停机，当天的记忆提炼、收件箱整理、周报草稿、每日简报才会整天缺失，之后也不补。
- **方案**：启动时检查前一天的执行标记，缺失且属于可重复的整理类任务时补跑一次。
- **验收**：模拟前一天全天停机，重启后 10 分钟内补跑前一天的整理任务。

### OPT-32 公众号素材缓存不复核；草稿是否被删只扫最近 100 条

- **证据**：`publish.go:585-592` 命中缓存直接复用 `media_id`；`r4.go:332-353` 只扫描最近 100 条草稿判断是否被删除。
- **方案**：上传素材遇到 40007（无效 media_id）时清除缓存并重传一次；草稿检测改为按 `media_id` 直接查询（`draft/get`），查不到再判定"可能已发布或已删除"。
- **验收**：在公众号后台删除素材后再写入草稿，自动重传成功；草稿超过 100 条时检测结果仍准确。

### OPT-33 小红书标题/正文字数上限未校验

- **证据**：`checks.go:148` 标题只检查非空，注释"字数上限待核实（V-012）"；无正文字数检查；公众号标题已校验 ≤ 32（`checks.go:136`、`publish.go:162`）。
- **方案**：先完成 V-012 实地核验（标题、正文上限及表情计数方式），再把上限加入检查与打包，计数沿用 `runeLen`。
- **验收**：超过核实上限的标题或正文在检查页给出明确提示，生成发布包前拦截。

### OPT-34 没有恢复演练脚本，没有异地备份

- **证据**：`deploy/backup.sh:20-25` 已备份数据库与 `/data`，保留 14 天；恢复只有手工文档 `deploy/restore.md`；没有异地副本。
- **方案**：新增 `restore.sh`，在临时 compose 项目中恢复最新备份并检查 `/healthz` 和一张图片；每月执行一次。异地备份用 rclone 加密同步到对象存储（用户自备账号）。
- **验收**：恢复脚本 10 分钟内完成并通过检查；异地存储中可见最近 7 天的备份。

### OPT-35 素材过期判断使用数据库 UTC 日期

- **证据**：`memory.go:218`、`:259` 使用 `current_date`；数据库容器未设时区（`deploy/docker-compose.prod.yml:39-47`），应用容器为 `Asia/Shanghai`。北京时间 0～8 点之间，"已过期"判断会晚一天。
- **方案**：数据库连接参数统一设 `timezone=Asia/Shanghai`（可与 OPT-03 一起做），或这两处改为传入 `s.today()`。
- **验收**：北京时间 00:30，有效期为昨天的素材显示为已过期。

### OPT-36 作品没有标签/分组

- **证据**：作品列表只有状态标签页和"保存视图"（`Works.tsx`），无标签或分组字段。
- **方案**：作品增加自由标签，列表支持按标签筛选；分组（文件夹）等确有需要再做。
- **验收**：可给作品添加/移除标签，按标签筛选，命令面板可搜索标签。

### OPT-37 没有手机扫码预览

- **证据**：`Preview.tsx` 只有桌面端手机外框预览；无预览链接或二维码。

- **验收**：手机扫码可看到与写入草稿箱一致的排版；链接过期后无法访问。

### OPT-38 单篇作品不能导出 Markdown

- **证据**：推送页、预览页可复制 HTML（`Push.tsx:111`、`Preview.tsx:191`）；数据导出页只导出整体数据（`Export.tsx`）。
- **方案**：编辑器"更多"中提供"导出 Markdown"（含图片链接）；Word 导出等确有需要再做。
- **验收**：导出的 Markdown 在常见编辑器中打开，标题、段落、图片顺序与作品一致。

### OPT-39 图片没有替代文字；小红书封面缺尺寸预设

- **验收**：图片库可编辑替代文字并写入排版 HTML；小红书作品生成的封面为 3:4。

### OPT-40 长列表没有虚拟滚动（潜在风险）

- **证据**：`src` 中无虚拟列表依赖；`Topics.tsx`、`Materials.tsx` 全量渲染。个人场景数据量通常不大。

- **验收**：1000 条素材时滚动保持 50fps 以上。

- **验收**：被修改的文件提交后不超过 800 行。

## 6. 第三轮：智能、动线与流畅（OPT-42 至 OPT-75）

第三轮专看前两轮没有深挖的三件事：AI 用没用好手上已有的信息（智能）；完成一件事要点几下、跳几页、会不会走进死胡同（动线）；连续操作时会不会闪、会不会丢、会不会误触（流畅）。每条结论都回到代码核对过；P1 写完整，P2 只写证据、方案和验收。

### 6.1 智能：AI 没用好已有的信息

#### OPT-42 选中的素材、观点与大纲会被按字数裁掉（P1）

- **问题**：06 文档约定"账号档案、观点和用户选中的素材不裁剪"，实际素材槽上限 4000 字、作品槽上限 3000 字，超出的素材整条丢弃，观点加大纲超长时从尾部截断。用户精心挑的素材、大纲后半部分模型看不到，结果是编造或写出"【待核实】"。上下文说明里会标出"已截断"，但用户很难注意到。
- **证据**：`server/internal/app/contextpack.go:14` `"materials": 4000, … "work": 3000`；`contextpack.go:399-406` 超预算的素材 `Truncated = true` 后不写入；`contextpack.go:278-279` `main = truncate(main, budget-1)`；`docs/06-数据与技术架构.md:238`。
- **方案**：按文档实现：选中素材和观点不参与裁剪；预算不够时先丢系列相邻作品，再把大纲中与当前段落无关的条目压缩为只保留小标题，当前段落对应条目始终完整。素材总长超过模型上下文的极端情况，给出明确提示"选中素材过长，请减少"，而不是静默丢弃。
- **收益**：起草内容"有据可依"，减少用户返工和事实错误。
- **成本**：S。
- **验收**：选中 6 条各 1000 字的素材起草，请求内容包含全部 6 条；10 段大纲的第 10 段起草时，提示词中有完整的第 10 条大纲；新增单元测试覆盖这两种情况。

#### OPT-43 段落改写、扩写不带素材和全文脉络（P1）

- **问题**：段落起草会带上素材、观点与大纲；改写、扩写、精简只带本段文字（截取 1500 字）。"扩写"没有可扩的事实来源，只能空泛展开或编造；改写也可能偏离全文观点。
- **证据**：`server/internal/app/writing.go:734-745`：提示词只有本段小标题、本段全文和选中内容，`aiTask` 未设置素材和作品信息。
- **方案**：复用起草时的取数逻辑，带上本段关联素材和精简版作品信息（观点 + 各段小标题）。扩写模式明确要求"只用素材中的事实展开"。
- **收益**：扩写和改写更贴题、少编造，是编辑器里使用频率最高的 AI 动作之一。
- **成本**：S。
- **验收**：对关联了素材的段落执行扩写，请求内容中出现素材与观点；上下文说明面板能看到素材槽。

#### OPT-44 标题生成不看账号风格、不避开近期标题，超字数候选照样返回（P1）

- **问题**：拟标题时跳过了账号风格样本，也没有把本号近期标题传给模型去重；系统已经统计出"本号高表现标题特征"（如含数字、提问式），但只用来给候选打标签，没有告诉模型。超过平台字数上限的候选也原样返回，用户只能自己挑掉。
- **证据**：`server/internal/app/writing.go:847` `aiTask{Type: "title", … SkipStyle: true}`；`writing.go:856` `highPerformingTitleFeatures` 在模型返回之后才调用；`writing.go:868` `c.OverLimit = c.Chars > maxLen` 只做标记。
- **方案**：①把近 20 篇标题和高表现特征写进提示词（"避免与这些标题雷同""本号读者对以下特征反馈更好"）；②带上风格摘要（不带完整样本，控制长度）；③校验函数剔除超字数和命中禁用词的候选，剩余不足要求数量时带原因重试一次。
- **收益**：标题是用户最在意、重复生成次数最多的环节，直接影响"AI 懂不懂我的号"的观感。
- **成本**：S。
- **验收**：返回给前端的候选中超字数为 0；提示词中包含近期标题与高表现特征；模拟模型返回 2 条超长标题时自动重试一次。

#### OPT-45 结构化输出重试时不告诉模型错在哪（P1）

- **问题**：模型返回的 JSON 解析失败或不合规时会重试一次，但重试用的是一模一样的提示词，模型大概率犯同样的错，白白多花一次费用，最后用户看到"格式不正确"。
- **证据**：`server/internal/app/aicore.go:306-323`：校验失败后 `continue`，`t.User` 未改动。
- **方案**：重试时在用户消息末尾追加"上一次输出不符合要求：{具体原因}。只输出修正后的 JSON"。截断导致的不完整 JSON 先尝试补全括号再解析。
- **收益**：45 类 AI 任务里有大量结构化任务，一处改动全部受益；接真实模型后格式错误是常见失败原因。
- **成本**：S。
- **验收**：模拟模型第一次返回少字段、第二次按提示修正，任务成功；第二次请求内容包含第一次的错误原因。

#### OPT-46 大纲、每日推荐、摘要等任务只能读到"通用"记忆（P1）

- **问题**：账号记忆按作用域（通用、正文、标题、选题）注入。大纲、大纲评审、每日推荐、摘要、改写方案、事实核查没有映射到任何作用域，只能读到"通用"记忆。用户确认过"先写结论再展开"这类正文记忆，生成大纲时却用不上。
- **证据**：`server/internal/app/aimemory.go:44-54` `taskMemoryScope` 只列出标题、选题、正文三组任务，其余返回空；`aimemory.go:57-58` 查询条件 `scope='all' OR scope=$2`。
- **方案**：大纲、大纲评审、摘要、改写方案归入"正文"；每日推荐归入"选题"；事实核查只读"事实"类记忆。补一张任务与作用域对照表进 06 文档。
- **收益**：用户确认过的偏好在更多环节生效，"教一次、处处记得"。
- **成本**：S。
- **验收**：新增一条"正文"作用域记忆后，生成大纲的上下文说明中出现该记忆；现有记忆测试不退化。

#### OPT-47 正文写完后"下一步"断档，发布后不提示派生（P1）

- **问题**：工作台的"今天的主线"和"智能下一步"依赖下一步规则。创作中的作品只在"还有空段落"或"观点/大纲未确认"时给出提示；正文全部写完但还没拟标题、没配封面时，这篇作品从下一步里消失了。公众号文章发布后也只提示录入数据，不提示"派生小红书笔记"。
- **证据**：`server/internal/app/nextactions.go:96-107`：`drafting` 分支只有两种情况，第三种（正文已写完）无任何提示；已写入草稿箱或已生成发布包之后，只提示回填发布状态（`nextactions.go:129-135`）、后台待办和数据录入。
- **方案**：在 `drafting` 分支增加：无标题 → "去拟标题"（链接到标题步骤）；无封面 → "去配封面"；都齐了 → "去排版检查"。已发布公众号文章且没有派生作品 → "派生一篇小红书笔记"（只是提示，由用户点开后手动操作）。
- **收益**：主线不再中途断掉，"打开就知道下一步做什么"在整条链路上成立。
- **成本**：S。
- **验收**：正文写完无标题的作品出现在下一步中并链接到 `#step-title`；新增规则单元测试；不出现任何"一键全部"类入口。

#### OPT-48 采纳与拒绝信号没有直接回流到候选生成（P2）

- **证据**：`server/internal/app/feedback.go:55-61` 记录了 `choice_index`、`edit_ratio`；除测试外没有读取 `choice_index` 的代码。记忆提炼会根据修改和拒绝原因生成"建议记忆"，但需要用户确认后才生效（`aimemory.go:57`）。
- **方案**：标题、选题生成时附一小段"最近采纳过的 / 明确拒绝过的写法"（各取 5 条原文和拒绝原因），不经过记忆确认，也不写入记忆。同一拒绝原因累计 3 次时，在记忆页醒目提示一键确认。
- **验收**：连续拒绝 3 个"太夸张"的标题后，下一次标题请求的提示词中出现这些拒绝样例。

#### OPT-49 事实核查不参考作者提供的素材（P2）

- **证据**：`server/internal/app/checks.go:459-476` 提示词只有标题和正文，`aiTask` 不带素材。
- **方案**：带上作品关联素材，要求模型把"素材中已有出处的句子"标为"有素材支撑"，只把没有出处的数据、引语、断言列为待核实；前端把两类分开显示。

### 6.3 流畅与可靠：连续操作时不闪、不丢、不误触

#### OPT-63 同一段的标题和正文分两次保存，可能自己和自己冲突（P1，已验证；触发频率未测）

- **问题**：正文停止输入 1.2 秒后保存，标题在失焦时单独保存，两个请求都带当前修订号。只要前一个请求还没返回、后一个已经发出（改完标题马上继续写正文，或网络稍慢超过 1.2 秒），后一个就会因修订号过期收到"这一段已在其他地方修改过"，没有别人编辑也会弹冲突对话框。
- **证据**：`web/src/pages/work/section-block.tsx:182-190` `persist` 每次都用 `revision.current` 直接发请求，没有串行；`section-block.tsx:231-234` 正文 1.2 秒防抖；`section-block.tsx:680` 标题 `onBlur` 单独 `persist({ heading })`；服务端 `server/internal/app/writing.go:343` 修订号不一致即返回 409。
- **方案**：每段一个保存队列：同一时间只有一个请求在途，期间的修改合并为下一次保存，且总是同时提交标题和正文；收到成功响应后用新修订号发出下一次。
- **收益**：消除"一个人写也弹冲突"的困惑，这是编辑器信任感的基础。
- **成本**：M。
- **验收**：把接口人为延迟到 3 秒，连续改标题、写正文 30 秒不出现冲突对话框，最终内容与修订号正确；新增前端单元测试覆盖排队合并。

#### OPT-64 关闭冲突对话框后，本地修改既没保存也没存本地草稿（P1）

- **问题**：保存前已把"有未保存修改"标记清掉；遇到冲突只弹对话框，不写本地草稿。用户按 Esc 或点遮罩关掉对话框后，编辑器里的文字还在，但服务端和本地草稿都没有；此时刷新或关页面，这段修改就没了。
- **证据**：`section-block.tsx:184` `dirty.current = false`；`section-block.tsx:198-200` 冲突分支只 `setConflict`，不调用 `writeDraft`（网络错误分支 202 行会写）；冲突对话框 `onClose={() => setConflict(null)}`（约 871 行）。
- **方案**：冲突时立即写本地草稿并恢复"未保存"标记；对话框关闭等同于"稍后处理"，段落上保留醒目的"有冲突待处理"标记，离开页面时提示。
- **收益**：堵住一个确定的丢稿路径。
- **成本**：S。
- **验收**：制造冲突后按 Esc 关闭对话框再刷新，页面提示恢复了未同步的修改。

#### OPT-65 中文输入法选词时按回车会直接提交（P1）

- **问题**：用拼音输入法时，按回车是确认候选词。多个输入框把回车当作提交，却没有判断是否处于输入法组字状态，结果是选词的同时触发了提交：选题方向框会直接开始 AI 生成（花费额度），命令面板会执行当前高亮的命令，重新验证密码框会提交。
- **证据**：全前端只有 `web/src/pages/Review.tsx:232` 判断了 `isComposing`；未判断的有 `Topics.tsx:131`、`Topics.tsx:171`（回车调用 `run()` 生成选题）、`Works.tsx:66`、`command-palette.tsx:303-305`、`dialog.tsx:136`、`quick-collect.tsx`、`editor-sidebar.tsx` 等共约 10 处。
- **方案**：封装一个回车判断函数（排除 `isComposing` 和 `keyCode 229`），所有回车提交统一使用；加一条 lint 规则或代码检查脚本防止回退。
- **收益**：中文用户每天都会碰到的误触，修复成本极低。
- **成本**：S。
- **验收**：在选题方向框用拼音输入"时间管理"并按回车选词，不触发生成；再按一次回车才触发。

#### OPT-66 小红书卡片编辑器没有冲突处理（P2）

- **证据**：`web/src/pages/work/CardEditor.tsx:102-107` 保存失败统一 `toast.error(errorMessage(e))`，修订号不会更新，后续每次保存都会继续冲突。

#### OPT-67 对话框不困住焦点，关闭后焦点不回原处（P2）

- **验收**：长文本中连续输入时，页面滚动位置不跳动。

#### OPT-75 零碎问题：重复提交与键盘可达（P2）

- **证据**：推送页"同步状态"按钮没有加载状态，可重复点击（`Push.tsx` 约 251-257 行）；重新验证密码框按回车时不检查是否正在提交（`dialog.tsx:117-136`）；检查页的问题卡片是可点击的 `div`，不能用键盘操作（`Check.tsx` 约 231 行）。
- **方案**：分别补加载状态、提交中忽略回车、改用按钮元素。
- **验收**：快速双击"同步状态"只发 1 个请求；检查项可用 Tab 和回车操作。

## 8. 核实后不成立或已具备的判断

| 初步判断 | 核实结论 |
| --- | --- |
| Go 按北京时间计算的"今天"写入数据库 `date` 列会错一天 | 不成立。pgx 按值自身的年月日编码日期（`pgtype/date.go:163`），SQL 中显式 `$n::date` 同理。唯一受影响的是使用 `current_date` 的两处，见 OPT-35 |
| 登录接口缺少限流 | 已具备：连续失败锁定 15 分钟（`auth.go:207/222`） |
| 流式输出缓冲满时会丢"完成"事件 | 不成立：缓冲 8192 条，正常输出远达不到 |
| 按 ID 访问的接口存在越权 | 抽查 10 个加载函数（作品、账号、图片、素材、系列、收件箱、参考号、批注、任务、漫画分格）均按工作区过滤，未发现越权 |
| 多实例同时启动会并发执行迁移 | 不成立：goose v3.28 迁移带数据库锁 |
| 已有 `/healthz` 不检查数据库 | 不成立：会以 1 秒超时检查数据库（`server.go:84-91`） |
| AI 任务完成通知缺少去重 | 不成立：每个任务只在结束时通知一次，重新发起是新任务，分别通知是正确行为 |
| 每日任务停机后一律不补跑 | 部分成立：3 点到 24 点之间任意时刻在线都会执行，只有整段停机才缺失，见 OPT-31 |
| AI 失败提示里"去模型配置"用 `pushState` 跳转，路由收不到 | 不成立：react-router v6 的 `BrowserRouter` 监听 `popstate` 并读取当前地址，`ai-error.ts:6-8` 能正常跳转。可顺手改为路由自带的跳转方法，但不是缺陷 |
| 协作时"正在编辑"提示最多滞后 10 秒 | 不成立：切换到新段落的第一次输入立即上报（`WorkLayout.tsx:273-277`），10 秒节流只作用于同一段落的重复上报 |
| 每日推荐"直接开始写"多一次确认，应改成一键 | 不建议：这一步是 H-01 选题入库的人工确认，已经是在卡片内展开、不跳页的最短形式 |
| 应缓存相同请求的 AI 结果以省费用 | 不建议：用户点"重新生成"就是要不同结果；真正的浪费在格式错误的盲目重试，见 OPT-45 |

已做得好的部分（不需要重复投入）：页面级懒加载与骨架屏；AI 流式、停止与刷新续接；断网本地草稿与修订号冲突对话框；首字超时、备用模型切换、每日 Token 上限与调用记账；优雅停机与 panic 恢复；部署前自动备份；热点采集预算、robots 与 SSRF 防护；段落历史保留 30 条；指标快照、每日推荐的唯一约束；公众号 token 行锁刷新；统一的自定义确认对话框。

第三轮补充确认做得好的部分：上下文槽位与"本次参考了什么"说明；记忆提炼必须用户确认才生效；大纲引用素材只允许白名单 id；每日推荐的依据必须来自已知候选；候选之间相似度控制；写回前绝对化用语自查；"今天的主线"一键直达下一步；AI 失败提示带重试和换备用模型；推送失败带重试、复制 HTML 和凭证入口；小红书发布包的复制、系统分享、打包与伴侣 App 交接；"最近打开"作品；作品列表筛选保存在地址中；4xx 不重试、401 直接回登录页；路由级错误边界；按钮加载态禁止重复点击；段落删除可撤销。
