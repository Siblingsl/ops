## 0. 维护约定

1. **一条一个问题**，追加到对应模块分区末尾；ID 一经分配不复用、不重排。
2. 每条必须包含：**位置**（`文件:行`，行号漂移时以函数/组件名为准）、**证据**、**影响**、**建议方向**、**严重度**、**状态**。
3. 状态只用：`待修` / `修复中` / `已修` / `待决策` / `不修`。`不修`必须写理由。
4. 修复后在同一行补 **任务号**（`DEV-xxx`）与 **验证方式**（测试名 / 手工步骤 / E2E）；不删除历史条目，必要时在条目末尾追加"后续"。
5. 新模块新轮次用新前缀，每轮在"索引"登记。已用前缀：第一轮 `NW`=新建作品；第二轮 `GL`=全局与导航、`DB`=工作台、`TP`=选题与收件箱、`WL`=作品列表与平台作品、`ED`=编辑与保存、`CK`=检查与审阅、`PB`=发布与回填、`MT`=素材与图片、`AG`=智能体、`OP`=运营/日历/档案/复盘、`ST`=设置与首次使用、`XC`=跨模块、`DOC`=文档自身。
6. 严重度：
   - **S1**：阻断核心承诺、可能丢内容、绕过人工门槛；
   - **S2**：明显影响首次成功或状态可信度；
   - **S3**：一致性、可维护性、清扫项。
7. 证据等级：`已验证（静态）`＝读代码/文档/测试确认；`已验证（运行时）`＝实际复现；`潜在风险`＝推断未复现。第二轮起大部分条目已有 E2E/单测佐证（`web/e2e/nw-*.spec.ts`、`server/internal/app/nw_*_test.go`），未覆盖项在对应分区"仍未覆盖"里逐条列明。

## 1. 新建作品（2026-10-22）

### 1.1 结论

1. **"新建作品"目前是一条立即落库的快捷方式，不是创作起点。** 通用入口以 `title: ''` 直接 `POST`，没有标题、来源（空白/选题/旧文）、形态或模板的选择。截图里的 `未命名作品` 不是偶发，是契约的必然结果。
2. **截图同时暴露另外三个结构性问题**：`检查中` 是打开检查页就自动进入、且无法退回 `drafting` 的状态；`笔记图片 0 / 18 张` 把上限读成目标；右栏在无段落作品上提示"点一下任意段落"。
3. **H-02 只挡住了"AI 生成大纲"和"起草"，没挡住"手动确认大纲"。** 确认后每段起草都会以 H-02 失败，形成"大纲已确认、却永远起不了稿"的死结。
4. **观点保存在 800ms 防抖里**，保存返回会用服务端值回写本地输入框，正在输入的字会被吞；同一窗口里"生成大纲"读的是服务端旧值。
5. **创建逻辑分散**：前端 3 份实现，服务端 5 条以上写路径；`insertWork` 的账号校验/审计只有一半入口享受得到。
6. **修复顺序**：先修 S1（丢字、H-02 绕过、检查自动开始、`checking` 不回落、重复创建），再统一创建契约与入口，最后做首屏引导与 DEV-416 模板。
7. **v0.2 进展**：第 1–6 条中的 S1 已按 P0 修复（观点回写、确认大纲 H-02、检查自动开始、`checking` 回落、创建幂等）；第 5 条的"创建逻辑分散"仍待 P1，第 2 条的首屏问题仍待 P2。

### 1.5 问题详情

#### A. 创建入口与创建契约

##### NW-A1 通用新建立即落空作品：标题、来源、形态全部零决策（S1 · 已修）

- **位置**：`web/src/pages/Dashboard.tsx:53`、`web/src/pages/Works.tsx:234`、`web/src/components/command-palette.tsx:223`；原型 `docs/design/desktop-creative/prototype/prototype.js:395`。
- **证据**：三处都发 `{title:''}`，拿到 `id` 直接 `nav`；`useCreateWork` 的 `title` 形参在全仓库没有任何调用方传值（只有 `Works.tsx:152`、`Dashboard.tsx:409` 两处引用，且都无参调用）。原型是一个含"作品标题（默认未命名作品）+ 作品形态 + 取消"的弹窗。
- **影响**：列表/最近打开/页头全部显示 `未命名作品`（`Works.tsx:297`、`WorkLayout.tsx:349`、`WorkLayout.tsx:491`），多篇空作品完全同名；用户没有机会在创建时写下"想表达什么"，而这正是产品的第一个主张。
- **建议**：创建即打开统一"新建作品"面板（标题可空但给占位、来源=空白/选题、形态仅头条、模板槽位）；或创建后把焦点直接落到观点并显示"先写一句观点"。不要再用 `title:''` 静默落库。
- **任务**：DEV-NW01：`nw-p1.spec.ts`（面板可见、标题占位、空标题创建、从选题开始）；`web/src/components/create-work-panel.tsx` 为唯一创建面板。

##### NW-A2 重复创建没有任何护栏（S1 · 已修）

- **位置**：`web/src/pages/Dashboard.tsx:53`、`web/src/pages/Works.tsx:234`、`web/src/components/command-palette.tsx:216`、`server/internal/app/works.go:325`。
- **证据**：三处都无 busy/lock；服务端无幂等键、无去重，`createWork` 每次 `INSERT`。对比之下选题的"开始创作"有 `loading={busy}`（`Topics.tsx:384`）。
- **影响**：双击、回车连点、两个标签页都可产生两篇空作品；叠加 NW-A1 后无法分辨。
- **建议**：前端 mutation `isPending` 锁按钮直到导航；服务端 `Idempotency-Key`，或 10 秒内同账号同标题去重。
- **任务**：DEV-NW01；验证：`TestNWA2_CreateWorkIsIdempotent`（同一 `Idempotency-Key` 两次创建返回同一作品；不同键仍可新建）；前端三处创建实现加连点锁并复用同一键。

##### NW-A3 创建响应被丢弃，二次全页加载；失败文案误导（S2 · 已修）

- **位置**：`web/src/pages/Dashboard.tsx:60`、`web/src/pages/work/WorkLayout.tsx:405`。
- **证据**：`POST` 已返回完整 `Work`，客户端只取 `id` 后 `nav`；`WorkLayout` 再用 `PageLoading variant="editor"` 重新 GET；GET 失败（网络/500）统一显示"作品不存在或已删除"。

## 2. 全站操作动线（2026-10-22，第二轮）

### 2.1 结论

1. **单点动线已经能走通，但"走通"依赖用户自己记住下一步。** 编辑器、检查、发布、回填各自都有明确的页头主按钮；一旦离开页头（滚到正文底部、进入结果卡、切到列表），下一步就消失。第二轮 70 条里，有 21 条属于"下一步只在页头/只在上一页"。
2. **同一个动作有多套叫法和多套入口。** "去检查"有 4 种文案（去检查 / 排版并检查 / 提交检查 / 下一步：发布前检查）；设置入口有 3 套清单（用户菜单 17 项、桌面设置窗 24 项、命令面板 14 项），名称还不一致。
3. **桌面端与网页端不是同一产品。** 桌面表现层隐藏了选题评分、素材多选、批量回填、平台指标刷新等能力，也改变了运营页的信息架构（6 个 tab vs 长滚动单页）；移动端则缺失 6 个一级入口。用户换设备后要重新学一遍。
4. **"今天该做什么"有 4 份互相竞争的列表**：主线（next-actions）、右栏今天的安排（todos 前 3）、全部作品待办（每列 6）、待回填（前 3）。排序规则不同、截断规则不同、出口不同。
5. **截断是静默的。** 作品列表服务端 `LIMIT 300`、待办每列 6 条、待回填前 3 条、搜索 60 条、平台作品 20/页；除平台作品外都没有"还有 N 条"或"查看全部"的可靠出口，用户会以为数据没了。
6. **状态可信度是这一轮最大的隐性风险。** "本周节奏"圆点按发布数量点亮而非真实日期；列表行点击按状态跳转，但"可发布"却进编辑器；复盘看板把未回填的 `pushed` 作品列成"尚未录入"却不提示先去回填。
7. **人工门禁本身是完整的，但门禁之外的"退回/放弃/撤销"普遍缺失。** 审阅只有"通过"没有"退回"；检查只有"完成"没有"放弃"；发布后锁定只读，页面内没有"解锁/标错了"。
8. **修复顺序建议**：先补"每一步的下一步"和"截断出口"（不改数据模型），再统一入口与文案（收敛到一份清单），最后处理桌面/移动分叉与门禁外的回退路径。

```
                     ↓                        ↓
              平台后台发表 ──────────────→ 回填已发布
                     ↓
              复盘录入（1/3/7 天）─→ 复盘报告 ─→ 选题建议 ─→ 选题池
```

**断点最密集的 5 个位置**：检查页底部（无下一步）、推送/发布包结果卡（无回填出口）、复盘看板（未回填不提示）、收件箱整理完成（无出口）、桌面/移动切换（入口与能力缺失）。

##### GL-08 桌面关窗绕过保存护栏（S2 · 待修）

- **位置**：`desktop/src/main.ts` `confirmApplicationQuit`（`before-quit` 与窗口 `close` 都走它）；对照 `web/src/lib/desktop-settings.tsx` `requestDesktopLeaveGuard`。
- **证据**：`confirmApplicationQuit` 只做 `dialog.showMessageBox`，确认后直接 `app.quit()`；渲染进程的 `DESKTOP_LEAVE_GUARD_REQUEST` 监听只在 `Shell.tsx`（切账号/切工作区/退出登录）与 `DesktopSettingsHost.tsx`（设置窗离开）里触发，Electron 主进程从不发这个事件。
- **影响**：编辑器里正在写的段落（1.2 秒防抖窗口内）在关闭窗口/退出应用时不会被拦截保存；用户点了"退出客户端"就失去最后几秒的输入。设置窗有 `beforeunload` 兜底，业务窗口没有对应拦截。
- **建议**：主进程在 `confirmApplicationQuit` 里先 `webContents.executeJavaScript` 触发一次 leave guard（或走 IPC 请求渲染层 flush），拿到 `false` 就取消退出；与设置窗行为对齐。
- **任务**：待定；验证：编辑器输入后立刻关窗，内容仍在。

##### GL-09 退出文案与实现矛盾（S2 · 待修）

- **位置**：`desktop/src/main.ts:2930` 的 `detail`：`客户端无法判断编辑器是否有未保存修改`。
- **证据**：同一份代码库里，渲染层已经实现了 leave guard，且 `Shell.tsx` 在多处调用；文案却说"无法判断"。
- **影响**：用户被引导去"手动先保存"，而系统本可以自动拦截；也说明维护者对自身能力的认知与代码不一致。

##### ED-12 小标题层级冲突（S2 · 待修）

##### ED-13 选区变了就替换到别处（S1 · 已修）

- **位置**：`web/src/pages/work/section-block.tsx:348`：`if (editor.current?.selectedText()) editor.current.replaceSelection(text)`。
- **证据**：生成时 `edit()` 在 271-272 行取 `sel = editor.current?.selectedText()`、`original = sel`，并把 `original` 存进 `Proposal`（309 行）。应用时 `applyText('selection', original, text)` 的 348 行**完全不看 `original`**，只要"当前有选区"就调 `replaceSelection(text)`；而 `replaceSelection`（`section-editor.tsx:84-90`）替换的是 `editor.state.selection` 的 `from/to`，即**当前**选区。
- **影响**：真实时间线——
  1. 用户选中 A 句，点「改写选中部分」；
  2. AI 返回，建议卡出现；
  3. 用户想先看看别处，重新选中了 B 句（或只是拖了一下选区）；
  4. 点「应用」→ 替换的是 **B**，A 原封不动。

  结果是"AI 针对 A 生成的内容被写进 B"，且 `onChange` 立即触发自动保存、`undoToast` 只提供 10 秒撤销。这是本轮唯一的 S1：静默改错内容。
- **建议**：应用前校验 `content.current.includes(original)` 且当前选区文本 === `original`；不一致时提示"选区已变化，请重新选中原文再应用"，并提供"按原文定位"按钮。
- **任务**：DEV-NW04。`Proposal` 增加 `range` 字段（生成时记录 `editor.selectionRange()` 的 from/to）；`EditorHandle` 增加 `selectionRange()`（`section-editor.tsx`：`RichEditor` 取 `editor.state.selection.from/to`，`PlainEditor` 取 `selectionStart/End`）；应用时双重校验——当前选区文本 === `original` **且** from/to 与生成时完全一致，任一不符即拦下。验证：`e2e/nw-r2p3.spec.ts` "ED-13" 已通过。

##### ED-14 兜底路径不判唯一（S2 · 已修）

- **位置**：`section-block.tsx:349`：`else if (original && cur.includes(original)) editor.current?.setMarkdown(cur.replace(original, text))`。
- **证据**：`cur.replace(original, text)` 只替换**第一次**出现；条件只有 `includes`（存在即可）。对照同文件 356 行的 `excerpt` 分支：`if (!original || cur.split(original).length !== 2)` —— 那里做了唯一性校验。同一个文件、同一个函数里，两个分支的严谨度不一致。

##### ED-15 建议卡无位置信息（S2 · 已修）

- **位置**：`section-block.tsx:626-630`：建议卡渲染 `proposal.original` 与 `proposal.text` 两栏。
- **证据**：只显示文本本身，不显示"在全文第几处""上下文前后各 N 字"；也不提示"当前选区与生成时不同"。

#### 2.15.2 复核：`applyText` 五个分支的定位可靠性

### 2B.2 CK-03 审阅退回：可行，但要加字段并定义语义

**现状约束**

- `work.status` 的 CHECK 是 `('drafting','checking','reviewing','ready','pushed','packed','published')`（`00007_v3.sql`），**没有** `returned`/`rejected` 这类状态。
- `work` 表只有 `reviewed_by`/`reviewed_at`（表示"已通过"），**没有任何退回原因字段**（全库 grep `reject|return_for|review_note` 在 `work` 表上零命中）。
- `approveReview`（`checks.go:914-947`）只做 `reviewing → ready`，并校验"owner 或指定审阅人、负责人不能审自己"。
- 关键发现：`touchContent`（`works.go:160-171`）的 CASE 里**已经包含 `reviewing`**——任何人修改内容，作品都会自动从"待审阅"回落到 `drafting`，且清空 `reviewed_by/reviewed_at`。

**这意味着什么**

"退回"在技术上有两条现成路径：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 不新增状态** | 退回 = 写一条 `review_comment` 记录 + 调用 `touchContent` 让状态回落 `drafting` | 零迁移、复用现有回落逻辑 | 退回与"内容被改"在状态上无法区分；审阅意见要另建表 |
| **B. 新增状态** | 加 `returned` 到 CHECK + 加 `review_note` 列 | 语义清晰、可统计"退回率" | 需要迁移、改 CHECK（PG 需重建约束）、前端状态徽标与筛选都要补 |

**推荐**：先做 A（1.5d 含前端），若产品确实需要"退回率"统计再升级到 B。A 的最小实现：

1. 新表 `work_review_note(id, work_id, author_id, note, created_at)`，或复用 `comment` 表（已有 `work_comment`，支持批注）；
2. 接口 `POST /works/{id}/review/return`，写意见 + 调用 `touchContent`；
3. 前端检查页加"退回修改"按钮（仅 `canApprove` 可见），弹窗填原因；
4. 通知负责人（复用 `notify`，`kind='review_returned'`）。

**必须先定的问题**：退回后是 `drafting`（作者要重新写+重检）还是 `checking`（只需重检）？按 `touchContent` 的现有行为，A 方案只能到 `drafting`。若要 `checking`，需要 B 方案或改 `touchContent` 的 CASE。

### 2B.3 CK-06 退出检查：可行，几乎零成本

**现状约束**

- 进入检查页本身不改状态（v0.2 已修 NW-D1，只有显式 `?start=1` 才发起检查）；但**一旦发起检查**，`startCheck` 会把状态置为 `checking`。
- 没有"退出检查"接口；唯一离开 `checking` 的方式是改内容（`touchContent` 回落 `drafting`）或完成检查。

**技术方案**（0.3d）

```go
// POST /works/{id}/checks/abandon
UPDATE work SET status='drafting', updated_at=now()
WHERE id=$1 AND status='checking'
```

- 不改表结构、不改 CHECK（`drafting` 已是合法值）。
- 检查记录保留（`check_run` 不删），只是不再"占用"状态。
- 前端：检查页页头加"退出检查"次级按钮，二次确认"检查记录会保留，作品回到创作中"。

**已核实的关键行为**：`startCheck`（`checks.go`）**每次调用都 `INSERT` 一条新 `check_run`**，并且先 `addVersion(reason='check')`。所以"退出后再进入"会**新建一次检查、重新逐项确认**，之前的 `resolution` 不会复用（`insertItems` 按新 run 写入）。

**这带来两个后果**：

1. 退出检查是"安全但费时"的操作——用户要重新确认一遍所有项；
2. 需要在二次确认里**明确告知**"退出后重新检查需要重新逐项确认"，否则用户会以为记录还在、结果白做。

若希望"退出后保留确认"，则不能走简单方案：需要在 `startCheck` 里按 `material_basis_hash` + `revision` 查找可复用的 run（当前没有这个逻辑），属于额外工作（约 1d）。建议第一版就按"重新确认"实现，并在 UI 说清楚。

### 2B.4 ST-10 解锁权限：**建议不修**，补文档即可

**现状**

- `unlockWork`（`works.go:754-769`）只校验 `confirm`，无角色检查；全局 `blockViewerWrites` 已拦住 viewer。
- 前端 `WorkLayout.tsx` 只在 `canWrite`（非 viewer）时渲染"解锁编辑"。

**文档依据**（决定性）

`docs/05-业务流程与交互.md:179` 原文：

> **已发布后修改**：已发布的作品默认只读。如需修改（例如修正错别字后在后台重新编辑），点击"解锁编辑"并二次确认；修改不会同步到平台，只更新系统记录。

同文档 566 行 E-14 也只写"需'解锁编辑'并二次确认"，**没有限定 owner**。

**结论**：当前"editor 可解锁"与文档一致，**不是缺陷**。建议把 ST-10 标为 `不修`，理由写"文档未限定角色；editor 负责内容，解锁属于内容操作"。若产品确要 owner 专属，才加 `requireOwner`（0.1d）并同步改文档。

### 2B.5 PB-06 发布包结构：只统一"回填区"，不强求整页同构

**现状对比**（实测两文件）

| 区块 | 小红书 `Pack.tsx` | 头条 `ToutiaoPack.tsx` | 是否共用 |
| --- | --- | --- | --- |

| 平台绑定 | `PlatformBinding` | 无 | ❌ 小红书独有 |
| 步骤说明 | "发布步骤" | "手动发布清单" | ❌ 文案不同 |

**为什么不能简单合并**

两页各约 300 行，共用部分只有 3 个组件；`CopyBlock` 与 `CopyField` 是两套复制实现，`PlatformBinding`（公众号/小红书绑定编号）与"分享预览"（头条独有）都是平台特有功能。

**可行方案**（2.5d）

1. **抽 `<PublishAside>`**：固定顺序 `HumanGate → 平台特有区块 → 待办 → 回填`，两页传入各自的"平台特有区块"；
2. **统一移动端 sticky**：抽一个 `<BackfillSticky platform>`，文案按平台取；
3. **`CopyField` 收敛到 `CopyBlock`**：头条的校验逻辑（`validateCopy`）作为可选 prop；
4. **不强求**：分享预览、平台绑定保持各自位置，只在文档里说明"为什么头条没有绑定"。

**收益**：回填入口在两种发布包里位置一致，直接支撑 P0 的 PB-01/PB-02。

**现状**

**扩展成本拆解**

**建议**：XC-05 降级为"文案说明"——在发布包页明确写"伴侣仅用于小红书，公众号/头条请用系统分享或复制"。成本 0.2d，避免用户误以为全平台可用。真要扩展，先做"深链带 `work_id` + 回填链接"（1.5d），不要做真回写。

## 2C. CK-03 审阅退回 · A 方案接口设计（可直接实施）

> 前置决策（2B.2）：退回后状态回 **`drafting`**，不新增 `returned` 状态、不改 CHECK 约束、不做数据库迁移。
> 设计原则：**复用现有 `comment` 表与 `touchContent`**，只新增 1 个接口 + 1 个前端入口 + 1 个通知 kind。

### 2C.1 已核实的现有能力

| 能力 | 现状 | 能否复用 |
| --- | --- | --- |
| 退回意见存储 | `comment` 表：`work_id`、`section_id`、`anchor_text`、`body`、`author_id`、`mentions`、`resolved_at`、`created_at` | ✅ 直接复用，无需迁移 |
| 内容变更回落 | `touchContent(ctx, tx, workID)`：`revision+1`、`checking/ready/pushed/packed/reviewing → drafting`、清空 `reviewed_by/at` | ✅ 正是退回所需 |
| 状态合法性 | `work.status` CHECK 含 `drafting` | ✅ 无需改约束 |
| 审计 | `s.audit(ctx, action, targetType, targetID, result, detail)` | ✅ 新增 action 名 |
| 通知 | `s.notify(ctx, ws, userID, kind, title, body, link, dedupeKey)` | ✅ 新增 kind |
| 路由注册 | `server.go` 中 `r.Post("/works/{id}/review/approve", ...)` 已有先例 | ✅ 紧邻注册 |

### 2C.2 接口定义

```
POST /api/v1/works/{id}/review/return
```

**请求体**

```json
{
  "note": "第二段的结论缺少数据来源，请补充后再提交检查。",
  "section_id": "3f2b...uuid",   // 可选：定位到某一段
  "mentions": ["user-uuid"]       // 可选：同时 @ 人
}
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `note` | string | ✅ | trim 后非空，≤ 2000 字（与 `createComment` 一致） | 退回原因，写入 `comment.body` |
| `section_id` | uuid \| null | ❌ | 必须属于该作品（`SELECT id FROM work_section WHERE id=$1 AND work_id=$2`） | 定位到段落；为空则整篇退回 |
| `mentions` | uuid[] | ❌ | 仅工作区活跃成员 | 复用 `resolveMentions` |

**成功响应** `200`

```json
{
  "work": { /* 完整 Work 对象，status 已为 drafting，revision+1 */ },
  "comment_id": "9c1e...uuid"
}
```

> 返回 `work` 与 `approveReview` 的 `writeWork` 保持一致，前端可直接 `setWork` 更新状态徽标，无需额外 GET。

**错误码**

| HTTP | code | 触发条件 | 文案建议 |
| --- | --- | --- | --- |
| 404 | `not_found` | 作品不存在/已删除/不属于当前工作区 | 作品不存在或已删除 |
| 409 | `state_invalid` | `status != 'reviewing'` | 这篇作品不在待审阅状态 |
| 403 | `forbidden` | 非 owner、非指定审阅人、非系统管理员代入 | 只有工作区所有者或指定的审阅人可以退回 |
| 400 | `validation` | `note` 为空或超 2000 字 | 请填写退回原因（最多 2000 字） |
| 400 | `validation` | `section_id` 不属于该作品 | 段落不存在 |
| 409 | `material_basis_stale` | 素材依据已变化（与 approve 一致） | 素材依据已变化，请重新检查 |

**权限判定**（与 `approveReview` 完全对齐，避免两套规则）

```go
isReviewer := reviewer != nil && *reviewer == id.UserID && (assignee == nil || *assignee != id.UserID)
if id.Role != "owner" && !isReviewer && !(id.SystemAdmin && id.AdminOverride) {
    return apiErr(403, "forbidden", "只有工作区所有者或指定的审阅人可以退回（负责人不能退回自己负责的作品）")
}
```

> 注意"负责人不能退回自己"这条：与 `approveReview` 的 `isReviewer` 判断一致，但 owner 不受限（owner 可以退回任何作品，包括自己负责的）。

### 2C.3 服务端实现骨架

```go
// returnReview is H-09 的对称动作：把待审阅作品退回给作者修改。
// A 方案：不新增状态，复用 touchContent 让 reviewing → drafting，退回原因存 comment。
func (s *Server) returnReview(w http.ResponseWriter, r *http.Request) error {
    m, err := s.workMetaFromPath(r)
    if err != nil {
        return err
    }
    var in struct {
        Note      string      `json:"note"`
        SectionID *uuid.UUID  `json:"section_id"`
        Mentions  []uuid.UUID `json:"mentions"`
    }
    if err := decode(r, &in); err != nil {
        return err
    }
    ctx := r.Context()
    id := ident(ctx)

    in.Note = strings.TrimSpace(in.Note)
    if in.Note == "" {
        return validation("请填写退回原因")
    }
    if runeLen(in.Note) > 2000 {
        return validation("退回原因最多 2000 字")
    }

    var commentID uuid.UUID
    var assignee *uuid.UUID   // 事务内查出，事务外用于通知
    err = s.withTx(ctx, func(tx pgx.Tx) error {
        var status string
        var reviewer *uuid.UUID
        if err := tx.QueryRow(ctx, `SELECT status, reviewer_id, assignee_id FROM work
            WHERE id=$1 AND deleted_at IS NULL FOR UPDATE`, m.ID).
            Scan(&status, &reviewer, &assignee); err != nil {
            return err
        }
        if status != "reviewing" {
            return stateInvalid("这篇作品不在待审阅状态")
        }
        isReviewer := reviewer != nil && *reviewer == id.UserID && (assignee == nil || *assignee != id.UserID)
        if id.Role != "owner" && !isReviewer && !(id.SystemAdmin && id.AdminOverride) {
            return apiErr(403, "forbidden", "只有工作区所有者或指定的审阅人可以退回")
        }
        if err := s.checkLatestMaterialBasis(ctx, tx, m.ID); err != nil {
            return err
        }
        if in.SectionID != nil {
            var x uuid.UUID
            if err := tx.QueryRow(ctx, `SELECT id FROM work_section WHERE id=$1 AND work_id=$2
                AND deleted_at IS NULL`, *in.SectionID, m.ID).Scan(&x); err != nil {
                return validation("段落不存在")
            }
        }
        // 退回意见写入 comment，author 为审阅人
        mentions := s.resolveMentions(ctx, in.Note, in.Mentions)
        if err := tx.QueryRow(ctx, `INSERT INTO comment
            (work_id, section_id, anchor_text, body, author_id, mentions)
            VALUES ($1,$2,'',$3,$4,$5) RETURNING id`,
            m.ID, in.SectionID, in.Note, id.UserID, mentions).Scan(&commentID); err != nil {
            return err
        }
        // 复用现有回落逻辑：revision+1、status→drafting、清 reviewed_by/at
        if err := s.touchContent(ctx, tx, m.ID); err != nil {
            return err
        }
        return nil
    })
    if err != nil {
        return err
    }

    s.audit(ctx, "review_return", "work", m.ID.String(), "ok",
        map[string]any{"checkpoint": "H-09", "comment": commentID.String(), "has_section": in.SectionID != nil})

    // 通知负责人；无负责人时通知所有者
    // 注意：workMeta 没有 AssigneeID 字段，需在事务内查出来，或扩展 workMeta。
    link := "/works/" + m.ID.String() + "?comment=" + commentID.String()
    target := assignee // 事务内 SELECT 得到的 *uuid.UUID
    if target != nil && *target != id.UserID {
        s.notify(ctx, id.WorkspaceID, *target, "review_returned",
            titleOr(m.Title)+"被退回修改", truncate(in.Note, 80), link,
            "review-return:"+m.ID.String()+":"+fmt.Sprint(m.Revision))
    } else {
        s.notifyWorkspace(ctx, id.WorkspaceID, []string{"owner"}, "review_returned",
            titleOr(m.Title)+"被退回修改", truncate(in.Note, 80), link,
            "review-return:"+m.ID.String()+":"+fmt.Sprint(m.Revision))
    }
    return s.writeWork(w, r, m.ID)
}
```

**实现要点**

1. **`workMeta` 没有 `AssigneeID`**（已核实 `works.go` 的 struct：只有 `ID/Account/ContentFormat/Status/Locked/Revision/Viewpoint/OutlineConfirmedAt/SourceWorkID/Title`）。事务里已经 `SELECT assignee_id`，需把 `assignee` 提到事务外声明（如骨架所示），**不要写 `m.AssigneeID`**。
2. **`FOR UPDATE` 锁行**：与 `approveReview` 一致，避免并发审阅/退回。
3. **`touchContent` 必须在同一事务**：它做 `revision+1` 与状态回落，与 comment 插入要么都成功要么都回滚。
4. **`revision` 会 +1**：这意味着退回后旧的 `check_run` 自动 `stale`（检查页会提示"内容在检查后又修改过"）。这是**期望行为**——退回本来就该重检。
5. **`dedupeKey` 用 `revision`**：同一次退回重复提交不会重复通知（虽然 `status` 已变，第二次会直接 `state_invalid`）。
6. **`resolveMentions(ctx, body, ids)`** 与 **`checkLatestMaterialBasis(ctx, tx, workID)`** 的签名已核实，与骨架一致，可直接调用。

| 场景 | 行为 |

### 2C.8 工作量与风险

| 项 | 估计 | 说明 |
| --- | --- | --- |
| 服务端 handler + 路由 | 0.5d | 骨架已给出，主要是复制 `approveReview` 的权限与事务结构 |
| 前端弹窗 + 按钮 + 横幅 | 0.5d | 复用现有 `Dialog`/`Field`/`Textarea` |
| 测试（15 条 Go + 1 条 E2E） | 0.5d | 大部分可参照 `approveReview` 现有测试 |
| **合计** | **1.5d** | 与 2B.2 估计一致 |

**风险**

1. **`revision+1` 的连带影响**：退回会让所有基于旧 revision 的检查、预览链接、打包依据失效。这是**语义正确**的，但要在 UI 说明"退回后需要重新检查"，否则作者会困惑为什么检查页突然要求重检。
2. **`comment` 表语义复用**：退回意见与普通批注混在一起。若不希望混，需加 `kind` 列（迁移 1 条），但会破坏 A 方案"零迁移"的前提。**建议先用 `anchor_text=''` + 作者是审阅人 来区分，暂不加列**。
3. **审阅人被移出工作区**：`reviewer_id` 仍指向旧用户，该作品会卡在 `reviewing` 无人能退（owner 除外）。建议在 `Members.tsx` 移出成员时检查其名下 `reviewing` 作品并提示 owner 重新指派（属 CK-03 之外的补强，可另立条目）。

### 2C.9 不在本方案范围

- **退回率统计**（需要新增状态或独立表）。
- **多次退回的历史视图**（当前只能在批注列表里看，无"第 N 次退回"聚合）。
- **退回后自动通知作者"要改哪几段"**（`section_id` 只记一段，多段需多条 comment 或结构化字段）。
- **`checking` 状态直接退回**（A 方案只能 `reviewing → drafting`）。
