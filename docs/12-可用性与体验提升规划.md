# 12 可用性与体验提升规划

- 状态：生效（2026-10-11）。来源：2026-10-10 的产品状态评估（D-049）。本规划只收录**可以通过开发交付**的解决项；需要用户人工操作的事项见第 6 节排除项。启动开发时按第 5 节规则在 08 文档拆分任务。
- 适用范围：整个产品的"能用 / 好用"提升。不改变任何红线（无发表/群发/定时发布/批量推送，无"全部起草/全部确认/全部入库"类批量按钮，不抓取平台后台数据，HC-01 至 HC-25 不放宽）。

## 1. 背景与评估结论

2026-10-10 的评估结论（详见对话记录与 D-049）：主链路与 V4 运营层在设计上完整、规则严谨，但"真实环境能用"未验证、"好用"未达到。差距归纳为八项：

| # | 问题 | 一句话证据 |
| --- | --- | --- |
| P1 | 关键链路只在 mock 上验证过 | 真实模型路由/草稿箱/出图从未实测，mock 模型是确定性的，只证明管道通 |
| P2 | 没有部署 | 本机开发形态；服务器、域名、HTTPS、备份、升级流程均为待办 |
| P3 | 数据回填闭环手工税高 | 复盘数据逐篇手动录入，公众号后台导出能力未验证（91 文档 V-011） |
| P4 | 热点现实价值未验证 | 第一批来源只过 mock；真实相关性/时效无观测工具支撑结论 |
| P5 | 首次价值路径太长 | 新账号需 配置模型→档案→样本→素材→方案→大纲 才有第一条推荐 |
| P6 | 逐段流程节奏感未经验证 | H-02/逐段确认是刻意设计，但"磨不磨人"取决于真实模型初稿质量 |
| P7 | 新界面只做到能用 | 卡片编辑器无排序、无单卡提示词编辑等（D-048 交付物） |
| P8 | 浏览器级验收欠债 | 每次发版界面回归靠人工，"浏览器人工验收待进行"反复出现在发版记录 |

## 3. 方案明细

### DEV-U101 模型与任务路由自检（P0 → P1）

- **现状与证据**：模型配置页只有连通性测试（chat 一句话）；JSON 模式、流式、图像生成、联网搜索四类能力是否正常，要等真正用到某任务时才知道，且报错发生在业务流程中。
- **目标**：用户配置完真实模型后，一次点击知道"这个模型能干什么、不能干什么、慢不慢"。
- **实施要点**：
  1. 后端 `POST /model-providers/{id}/selftest`：对该服务商逐项探测——①chat 连通；②JSON 模式输出可解析；③流式返回分块；④图像生成（小尺寸）；⑤若配置了原生联网搜索则探测一次搜索。全部标记 `is_eval` 类用量或直接不落 `ai_call`（避免污染统计），复用 `ai_key_invalid` / `ai_upstream_error` 的可读错误文案。
  2. 前端模型配置页加"运行自检"按钮，结果表格显示每项 成败/耗时/错误信息。
- **验收**：mock 模型自检全过；错误密钥时五项给出可读诊断；自检不产生质量看板/用量统计噪声。

### DEV-U102 公众号发布链路预检（P0 → P1）

- **现状与证据**：凭证"保存并检测"只验证 access_token；素材上传、封面 thumb_media_id 行为（V-015）、图片消息链路要到第一次真实推送才暴露问题。
- **目标**：推送前知道"这台服务器到公众号的完整链路通不通"。
- **实施要点**：
  1. 后端 `POST /accounts/{id}/wechat/link-check`：用 `add_material` 上传一张 1×1 测试图（走既有素材上传链路），返回 media_id 与耗时；不写草稿、不发表。
  2. 前端凭证面板在"保存并检测"旁加"链路预检"；结果与 V-015 的两个问题分开展示（上传成败 / 草稿读取稳定性留给首次真实推送验证，页面上如实说明）。
- **验收**：mock 微信下预检通过并返回素材 id；未配凭证时按钮不可用；不产生 push_record。

### DEV-U103 生产部署交付物（P0 → P2）

- **现状与证据**：deploy/ 只有 dev compose（本地数据库）；AGENTS.md 明确"部署到现有服务器与域名"是待办。
- **目标**：一条命令在任意一台 Linux 服务器上以生产形态跑起来（数据库 + 服务 + 自动 HTTPS），密钥全部来自环境变量。
- **实施要点**：
  1. `deploy/docker-compose.prod.yml`：Postgres（数据卷）+ ops 服务（构建 Dockerfile，若无则补）+ Caddy（自动 HTTPS 反代）。
  2. `deploy/.env.example` 补齐生产所需：`OPS_MASTER_KEY`、`OPS_PUBLIC_IP`、`OPS_CRAWL_MODE`、域名、数据库口令；与 06 文档第 7 节逐项对齐。
  3. 服务 Dockerfile 多阶段构建（含前端静态产物内嵌或 Caddy 托管二选一，按 06 文档 2.2 节拓扑定）。
- **验收**：本地用 prod compose 起一套（Caddy 用自签/本地域名），浏览器走通登录与一次完整创作链路；`docker compose config` 校验通过。
- **排除**：购买服务器、注册域名、备案为人工操作，不在本任务内。

### DEV-U104 备份与恢复（P0 → P2）

- **现状与证据**：无任何备份机制；数据含用户作品、凭证密文，丢失不可接受。
- **目标**：每日自动备份 + 明确的恢复步骤 + 保留策略。
- **实施要点**：
  1. `deploy/backup.sh`：`pg_dump` + assets 数据目录 tar，输出带日期文件名；保留 14 天；可用宿主 cron 或一个轻量 cron 容器调度。
  2. `deploy/restore.md`：恢复步骤（停服务 → 恢复库 → 恢复 assets → 起服务 → /healthz 验证）。
  3. 在 prod compose 注释中标注备份卷挂载点。
- **验收**：本地演练一次完整 备份→删库→恢复→健康检查 流程并记录耗时；文档步骤与实际一致。

### DEV-U105 升级回滚与健康检查（P0 → P2）

- **现状与证据**：`/healthz` 只返回 "ok" 不查数据库；goose 迁移无回滚演练；升级流程未文档化。
- **目标**：升级是"构建→迁移→切换"的可重复操作，出问题能回到上一版。
- **实施要点**：
  1. `/healthz` 增加 DB ping（1 秒超时），失败返回 503；compose 加 healthcheck。
  2. `deploy/upgrade.md`：升级步骤（备份→拉新镜像→migrate→启动→healthz 验证）与回滚步骤（前一镜像 + 恢复备份；goose Down 仅限无新类型数据的场景，与 D-048 迁移说明一致）。
- **验收**：本地演练一次 升级→验证→回滚→验证；healthz 在停库时返回 503。

### DEV-U106 粘贴批量回填（P0 → P3）

- **现状与证据**：`metric_snapshot` 为逐篇手动录入（reads/likes/wows/favorites/comments/shares/follows_gained）；发布多了以后手工税高，复盘飞轮（EX-S-02）依赖这份数据。
- **目标**：把"逐篇填表"变成"粘贴一次、确认一行"，仍是人工提供数据 + 逐行确认，不自动抓平台。
- **实施要点**：
  1. 后端 `POST /accounts/{id}/metrics/parse`（只解析不落库）：输入粘贴文本，按制表符/多空格/竖线切列，标题模糊匹配本账号作品（复用标题 trgm 索引），返回 匹配结果 + 未匹配行。
  2. 后端 `POST /accounts/{id}/metrics/batch`：确认后逐行写入 `metric_snapshot`（captured_at=当天）；单行失败返回行号与原因，不做部分静默成功。
  3. 前端复盘页新增"粘贴回填"：粘贴 → 预览（绿=可写入、黄=模糊匹配请确认、红=未识别）→ 确认写入。
- **验收**：给定三行样例（公众号后台可复制的格式 + TSV）解析正确；一行列数错误时该行标红且不影响其他行；红线检查——不发起任何对平台的请求。
- **说明**：V-011（后台数据能否导出）出结论后，若可导出文件再评估"文件导入"，本任务不做。

### DEV-U107 提示词模板包真实模型评测通路（P0 → P6）

- **现状与证据**：逐段流程的"磨人程度"取决于真实模型初稿质量；提示词回归（prompt_eval_case）已有，但用例是 mock 输出保存的，未提供"换真实模型批量跑一遍看结果"的操作路径。
- **目标**：用户配上真实模型后，能一键把关键任务（topic_suggest、daily_recommend、outline、section_draft、comic_storyboard、card 卡片大纲）的历史用例批量重放，得到结构合规率与输出样本，为人工校准模板提供依据。
- **实施要点**：
  1. 后端 `POST /prompt-evals/run-batch`：选定任务类型集合，逐用例以当前路由真实调用（标记 `is_eval`，计入用量），汇总：JSON 解析成功率、校验失败原因分布、输出长度分布、逐条输出文本。
  2. 前端提示词回归页加"用当前模型批量重放"入口与结果表；不提供自动改写提示词，模板修改仍由人进行（EX-F/FR-M12 边界）。
- **验收**：mock 模型下批量重放全绿且计为评测用量；禁用词/待核实标记规则在结果表中可见；单任务用例数上限沿用现有回归约束（防跑飞）。

### DEV-U108 热点来源健康度报表（P1 → P4）

- **现状与证据**：采集日志页有单次记录；但"哪个来源值得留着"缺 7/30 天汇总（成功率、条目量、被匹配量、转选题量、推荐采纳量）。
- **目标**：让人工观察"第一批来源价值"时有数可看，支撑来源增删决策。
- **实施要点**：超管采集页新增"来源健康度"区块：按来源聚合 `crawl_run`（成功/失败/条目数）、`account_hot_match`（匹配数、转选题数）、推荐 basis 归因（hot 依据被采纳数）。只读查询，不改采集逻辑。
- **验收**：mock 数据下各列数值正确；空来源显示"暂无数据"；不新增任何采集请求。

### DEV-U109 首次价值提速（P1 → P5）

- **现状与证据**：新账号到第一条推荐需 配置模型→档案→样本→素材→方案→大纲 六步；健康度清单已存在但按"完整度"排序，不是按"通往第一条推荐"的最短路径排序；`next-actions`（V425）已有下一步推荐能力。
- **目标**：新账号 10 分钟内（mock 环境）看到第一条推荐。
- **实施要点**：
  1. 工作台"下一步"按依赖排序为：配置模型 → 粘贴 1 篇旧作品建档（profile_bootstrap，可跳过）→ 起号向导启用方案 → 生成今日推荐；每步标注预计耗时与"可跳过"。
  2. 风格样本、素材等完整度项移到"进阶提升"分组，不再阻塞首屏"下一步"。
  3. 今日推荐/热点/大纲空状态的按钮直接执行对应动作（部分已有，统一化）。
- **验收**：浏览器走查：注册→(mock 模型自动种子)→粘贴一篇建档→问卷启用方案→生成推荐，全程 ≤ 10 分钟且无死路提示；健康度总分逻辑不变（仅入口重排）。

### DEV-U110 浏览器冒烟自动化（P1 → P8）

- **现状与证据**：回归到 API 层为止；界面回归靠人工，发版记录反复出现"浏览器人工验收待进行"。
- **目标**：一条命令跑完界面冒烟，人工验收只覆盖新功能与视觉。
- **实施要点**：
  1. web/ 引入 `@playwright/test`；`pnpm e2e` 启动/复用 `OPS_DEV=1` 的后端（:8080）+ 前端 dev server，全 mock 环境。
  2. 五条冒烟：①注册→添加账号→新建作品→大纲→起草→检查→小红书打包；②注册→方案启用→生成推荐→adopt；③账号类型锁定（设置页只读 + PATCH 拒绝提示展示）；④卡片流（大纲确认→逐卡生图→打包含文案）；⑤派生入口对新类型置灰。
  3. 测试数据用独立用户注册，避免污染 HC/API 测试数据库（复用 ops_test 机制或独立库，落地时定）。
- **验收**：`pnpm e2e` 本地全绿且可重复运行；Go 测试套件不受影响；08 第 6 节测试策略补充该层说明。

### DEV-U111 卡片编辑器打磨（P2 → P7）

- **现状与证据**：D-048 交付的 CardEditor 支持逐卡编辑文案与生成配图，但无卡片排序、无单卡提示词输入、重新生成会直接覆盖现图。
- **目标**：卡片流达到与漫画工作流相当的操作完整度。
- **实施要点**：
  1. 卡片上移/下移（复用 `PUT /works/{id}/sections/order`，`work_card.position` 随段落位置刷新）。
  2. 单卡"生成配图"支持可选提示词输入（接口已支持 `prompt` 参数，补前端输入）。
  3. 重新生成前二次确认并提示旧图保留在图片库/资产中（asset 记录不删，界面说明去重逻辑）。
- **验收**：浏览器走查三条操作；排序后打包与图片消息顺序一致（自动化断言）。

### DEV-U112 编辑器逐段起草键盘流（P2 → P6）

- **现状与证据**：逐段起草需"点起草→等待→手动滚动到下一段"；逐段确认是红线内的设计底线，不改变，但等待后的焦点/滚动可以自动化。
- **目标**：连续起草时手不离开键盘。
- **实施要点**：起草 SSE `done` 后自动滚动并聚焦下一段的"起草"按钮；`Ctrl+Enter` 直接触发下一段起草（等价于单击，不批量发起）。
- **验收**：浏览器走查连续起草 3 段无需鼠标；确认门槛（H-02/H-03）行为不变；无任何"多段同时发起"。

## 4. 与既有规划的关系

- 不改变 04/05/06/11 的功能定义；本规划是横切的质量与体验层。落地时若涉及数据表/接口，按第 5 节同步 06 与 05。
- DEV-U107 依赖但不同于既有"提示词回归"（FR-M12）：回归是保存用例与对比，本项是"当前模型批量重放"的操作入口，复用同一套用例存储。
- DEV-U106 严格维持"人工提供数据 + 逐行确认"边界，是 EX-S-02 飞轮的手工减负，不是自动化采集。

## 5. 任务管理与排期规则

- 启动开发时：在 08 文档新增第 4.11 节，按本表登记任务与完成状态；每个任务遵守"先写复现/验收测试再实现、一次一个任务小步提交、提交信息含任务编号"。
- 优先级顺序建议：DEV-U101 → U102 → U103 → U104 → U105 → U106 → U107（P0 一组）；之后 U109 → U110 → U108（P1）；U111、U112 随版本穿插（P2）。
- 文档同步：每完成一项，更新本表状态列与 08 对应行；涉及数据/接口的同步 05/06。

## 6. 排除项（需要用户人工操作，不列入开发任务）

| 事项 | 为什么排除 | 开发侧的配合 |
| --- | --- | --- |
| 提供真实模型密钥、公众号 AppID/AppSecret | 用户资产与账号操作 | DEV-U101/U102 把试错成本降到一次点击 |
