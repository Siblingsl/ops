## 1. 需求拆解与现状差距

### 1.1 需求拆成三件事 + 一个底座

| 需求 | 用户想要的结果 | 依赖 |
| --- | --- | --- |
| 起号定位 | 每个账号有一份明确的"运营方案"：赛道、目标读者、差异化、内容支柱、发布节奏、所处阶段。AI 能帮新号从零给出方案，也能帮老号复盘后调整 | 账号档案、样本、复盘数据、赛道热点（可选） |
| 运营大纲 | 方案落到"这个月 / 这周写什么"：按内容支柱和节奏排出计划槽位 | 运营方案、内容日历 |
| 每日热点 | 每天打开账号，看到**和这个账号相关**的热点，而不是全网热榜原样堆放；每条热点说明"为什么和你有关、可以从什么角度切入、有没有风险" | 热点采集底座、账号方案（关键词、支柱） |
| 每日作品推荐 | 每天给出今天该写的 1–3 个选题（加 2 个备选），每个推荐说明来源：来自哪个内容支柱、哪条热点、哪些素材、哪次复盘结论 | 运营方案 + 大纲 + 每日热点 + 素材 + 复盘 |
| 采集底座 | 能从公开热榜、RSS、模型联网搜索等来源拿到真实热点；强度可调、可一键关闭 | 新增 |

### 1.2 现状

| 能力 | 现状（代码位置） | 差距 |
| --- | --- | --- |
| 定位档案 | `account_profile`：定位标签、目标读者、人设语气、禁用词、风格摘要；`profile/bootstrap` 只能根据旧作品反推档案 | 没有赛道、差异化、内容支柱、节奏、阶段、目标；新号没有旧作品时无法建档；没有"方案版本" |
| 选题建议 | `topics/suggest`、`topics/hot-suggest`（`topics.go`），都要用户手动点；hot-suggest 只能靠用户粘贴资讯，提示词里写死"禁止使用热榜" | 没有真实热点数据；不会每天主动给 |
| 计划 | 内容日历 `planned_date`、系列 `topic_series`、下一步 `next-actions` | 没有"从方案生成大纲槽位" |
| 账号健康度 | `accountHealth`（`planning.go`）纯规则评分 | 不评估"定位是否清晰、节奏是否达标" |
| 后台任务 | `ai_job` 任务池、`jobs.go` 每 10 分钟的维护循环、周报 | 没有每日生成机制 |
| 检索 | `content_embedding` + `search_tsv` + trgm | 可直接用于热点与账号的相关度计算 |
| 外部数据 | 仅微信官方接口和模型接口 | 没有任何热点来源 |

结论：**账号层缺"运营方案"这一层抽象，选题层缺"真实热点输入"和"每日主动推荐"**。三块功能都应挂在"账号运营方案"下面，而不是各自独立。

### 2.3 "适当爬取"的合规边界

采集的主要风险不是技术，而是**对方网站的协议、反不正当竞争和刑事红线**。国内已有多起"抓取数据被判不正当竞争"的判例，判定重点通常是：是否绕过技术措施、是否抓取非公开数据、是否大量抓取并替代对方服务、是否造成对方服务器负担。更严重的是：**破解或绕过平台的技术防护去获取数据，可能构成刑法第 285 条"非法获取计算机信息系统数据罪"**，已有因破解平台加密参数抓取数据被判刑的案例。因此"避免触发风控"在本系统里的含义是**把量压到不触发**，而不是**触发了想办法绕过去**。

**第一部分：所有来源都必须遵守（写进代码，参数无法放宽）**

1. **只抓公开内容**：不登录、不带 Cookie、不使用任何账号；遇到登录页、验证码、滑块直接停止该来源，不尝试绕过。
2. **热榜类只抓榜单元数据**：标题、排名、热度值、分类、原文链接、上榜时间。不抓评论、不抓用户个人信息。小红书笔记和公众号文章的正文规则见第 3.5 节。
3. **遵守 robots.txt**：每个来源启用前检查一次并缓存 24 小时；robots 禁止的路径不抓。这一项不做成可关闭的开关。若某平台的 robots 禁止所需路径，该适配器在页面上显示"robots 不允许"并保持停用。
4. **低频**：单来源最短间隔 10 分钟（代码下限），默认 60 分钟；小红书、公众号另有更严的限额（第 3.2 节）；每天全站请求总数有上限。
5. **固定身份**：请求头使用一个固定的常见浏览器 User-Agent（部署时可改），**不轮换 UA、不轮换代理 IP、不伪造设备指纹**。
6. **只做内部参考**：采集结果只在系统内展示给本工作区用户，不对外提供、不转载、不做成公开榜单页。
7. **单点关闭**：部署环境变量 `OPS_CRAWL_MODE=off` 时，界面无法开启，代码中所有采集请求直接返回。

**第二部分：明确禁止的"规避风控"手段（任何参数都无法打开）**

| 禁止项 | 原因 |
| --- | --- |
| 逆向或伪造平台的签名参数（例如小红书接口的 `x-s`、`x-t` 等加密头） | 属于绕过技术保护措施，刑事风险 |
| 自动识别或打码平台破解验证码、滑块 | 同上 |
| Cookie 池、账号池、借用任何人的登录态（包括本系统所运营账号的） | 违反平台协议；被风控会连带封禁运营账号 |
| 代理 IP 池轮换、UA / 指纹轮换 | 目的就是规避对方的频率限制 |
| 无头浏览器、模拟器、自动化框架（Playwright、Puppeteer、Appium 等） | AGENTS.md 红线 |
| 调用平台 App 的私有接口 | 非公开接口，属于逆向 |

**结果的诚实预期**：在上述约束下，小红书大部分内容（搜索、话题页、用户主页列表）需要登录或签名，**系统拿不到**；能拿到的主要是"已知链接的单篇公开页面"。公众号文章的单篇链接通常是公开页面，可以读取，但没有公开的"某账号文章列表"或"公众号热榜"可供发现。因此这两个平台的采集定位是"**对标与参考：读取用户提供或从其他来源发现的单篇链接**"，而不是"全平台热点发现"（第 3.5 节）。DEV-V401 核验后以实际可达性为准。

> 说明：本节是产品层面的风险控制，不是法律意见。每个具体来源在启用前要做一次核验（第 10 节 DEV-V401），结果登记到 91 文档。

### 2.4 热点内容本身的风险（蹭热点）

微信 3.27 运营规范和小红书社区规范都打击"恶意蹭热点、借灾难事件营销、编造热点细节"。因此：

1. 每条热点在和账号匹配时，AI 同时给出**风险标签**：`disaster`（灾难事故）、`tragedy`（伤亡悲剧）、`politics`（时政敏感）、`unverified`（来源单一或未证实）、`commercial`（明显商业推广）。
2. 带 `disaster`、`tragedy`、`politics` 标签的热点**不进入每日推荐**，只在热点页灰显展示，并提示"不建议借此营销"。
3. 每日推荐中引用热点时，必须附原文链接；AI 不得补充榜单上没有的事件细节（事实核查规则沿用）。

## 3. 采集底座与"适当爬取"参数（模块 T）

### 3.1 来源类型

| 类型 | 说明 | 举例（**均待核验**，见 DEV-V401） | 默认 |
| --- | --- | --- | --- |
| `hotlist` | 平台公开热榜页面或公开接口，免登录可访问 | 微博热搜、百度热搜、今日头条热榜、B 站热门、知乎热榜、抖音热榜 | 关闭 |
| `rss` | 媒体或站点的 RSS / Atom 订阅 | 36 氪、少数派、澎湃、行业垂直媒体；用户可自行添加 | 关闭 |
| `search` | 模型自带的联网搜索（复用已配置的模型服务商） | 百炼联网搜索、火山方舟联网插件 | 关闭（需服务商支持） |
| `aggregator` | 自部署的开源热榜聚合服务（例如 DailyHotApi），本系统只调它的接口 | 部署在同一台服务器的聚合服务 | 关闭 |
| `xhs_page` | 小红书单篇笔记的公开页面（免登录可见部分） | 用户在"对标"里添加的笔记链接；其他来源中出现的小红书链接 | 关闭；敏感平台限额 |
| `wechat_page` | 公众号单篇文章的公开页面 | 用户添加的文章链接；RSS、聚合、热榜中出现的公众号链接 | 关闭；敏感平台限额 |
| `manual` | 用户粘贴的资讯摘要（现有能力保留） | — | 开启 |

**敏感平台域名**：`xiaohongshu.com`、`xhslink.com`、`xhscdn.com`、`mp.weixin.qq.com` 只允许 `xhs_page`、`wechat_page` 两个适配器访问，并且一律走第 3.2 节"敏感平台"限额。其他适配器（例如通用 RSS、原文摘要抓取）请求这些域名时，转交给对应适配器排队，而不是直接请求（HC-24）。`mp.weixin.qq.com` 下的微信官方接口调用（写草稿、datacube）不经过采集器，不受影响。

每个来源实现同一个适配器接口：

```go
type HotSource interface {
    Key() string                     // weibo、baidu、rss:<id> …
    Kind() string                    // hotlist | rss | search | aggregator
    Fetch(ctx context.Context, lim Limits) ([]HotItem, error)
}
```

所有出站请求统一经过一个 `crawlClient`：在这一层强制执行 robots、域名黑名单、无 Cookie、UA、超时、限速、熔断。适配器自己不能直接用 `http.Client`（代码审查规则 + 单元测试）。

### 3.2 参数：三层控制

**第一层：部署级（环境变量，优先级最高）**

| 变量 | 取值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `OPS_CRAWL_MODE` | `off` / `allow` | `off` | `off` 时整个采集功能不可用，界面显示"部署方未开启"。`allow` 时由超级管理员在界面上进一步控制 |

**第二层：全站级（超级管理员，"系统设置 → 热点采集"页）**

| 参数 | 取值 | 默认 | 代码硬上限 |
| --- | --- | --- | --- |
| 采集强度 `crawl.level` | `off` 关闭 / `conservative` 保守 / `standard` 标准 | `off` | 不提供更高档 |
| 单来源最短间隔 | 分钟 | 保守 60、标准 20 | ≥ 10 |
| 单来源每次最多条数 | 条 | 保守 50、标准 100 | ≤ 100 |
| 全站每日请求上限 | 次 | 保守 300、标准 1000 | ≤ 2000 |
| 原文摘要抓取 | 开 / 关 | 关 | 仅标准档可开；只请求与账号匹配度最高的原文链接页的 `<title>` 与 `meta description`，每天 ≤ 20 次 |
| 来源开关 | 每个来源单独开关 + 间隔覆盖 | 全关 | 覆盖值不得低于硬上限 |
| 熔断 | 连续失败次数 / 暂停时长 | 3 次 / 6 小时 | 遇到 403、429、验证码页立即暂停该来源 24 小时并通知超管 |
| 数据保留 | 天 | 14 | ≤ 60 |

**敏感平台限额（小红书 `xhs_page`、公众号 `wechat_page` 各自独立计算，单独开关）**

| 参数 | 保守 | 标准 | 代码硬上限 |
| --- | --- | --- | --- |
| 两次请求的最小间隔（同一平台，全站） | 10 分钟 | 5 分钟 | ≥ 3 分钟 |
| 每次间隔额外随机等待 | 0–5 分钟 | 0–3 分钟 | — |
| 每日请求上限（同一平台，全站） | 30 次 | 80 次 | ≤ 100 |
| 同一链接重复读取间隔 | 72 小时 | 24 小时 | ≥ 12 小时 |
| 允许时段 | 08:00–23:00 | 08:00–23:00 | 夜间不请求 |
| 风控熔断 | 出现登录墙、验证码、滑块、403、429、内容被替换为"环境异常"等提示页：立即停该平台 24 小时；7 天内第二次触发停 7 天，并把该平台开关自动置为"关闭"，需超管手动重新打开 | 同左 | 不可关闭 |

说明：这组数值的目标是让请求节奏接近"一个人偶尔点开几篇文章"。单台服务器、固定 IP，每天几十次单页访问，远低于正常用户的浏览量。随机等待只用来把请求在时间上打散，不是为了伪装身份。

三档的含义（写在页面上，让操作者看得懂）：

| 档位 | 一句话说明 |
| --- | --- |
| 关闭 | 不发出任何采集请求。热点功能只用"粘贴资讯 + 模型常识"，和现在一样 |
| 保守 | 每个来源一小时最多看一次榜单，只记标题和链接。适合日常使用 |
| 标准 | 二十分钟看一次榜单，可以给最相关的少量热点补一句原文摘要。热点变化快的赛道使用 |

小红书、公众号的开关在页面上单独成组，标题为"小红书 / 公众号页面读取（低频）"，并常驻一行提示："只读取免登录可见的单篇页面；碰到验证码或登录要求会自动停止，不会尝试绕过。"

**第三层：工作区与账号级（工作区所有者 / 编辑）**

| 参数 | 位置 | 说明 |
| --- | --- | --- |
| 本工作区使用的来源 | 工作区设置 → 热点来源 | 只能从超管已开启的来源里选 |
| 自定义 RSS | 同上 | 工作区可添加自己的 RSS 地址（经过同一个 `crawlClient`，同样受限） |
| 账号启用热点 | 账号运营方案 → 热点设置 | 关闭后该账号不做热点匹配，每日推荐只用支柱与素材 |
| 账号追踪关键词 | 同上 | 由运营方案自动生成初稿，人可增删；最多 30 个 |
| 账号屏蔽词 | 同上 | 命中则不展示该热点 |
| 手动刷新 | 今日热点页"刷新"按钮 | 触发一次匹配（不触发额外采集，除非距上次采集已超过最短间隔）；冷却 10 分钟 |

### 3.3 运行方式

1. **采集与账号解耦**：热点条目 `hot_item` 是全站共享的公开数据（不属于任何工作区），每个来源按间隔只抓一次，所有账号共用。这样请求量与账号数量无关，也最"克制"。
2. 采集循环挂在现有的后台维护循环里（`jobs.go`），每分钟检查一次"哪些来源到点了"。代码与路由命名**不使用** `schedule`、`cron`、`timer`（HC-05 路由扫描会拦截），使用 `refresh`、`collect`、`daily` 等词。
3. 每次采集写一条 `crawl_run`（来源、开始结束时间、HTTP 状态、条数、错误、请求次数），超管可在"采集日志"查看。
4. 去重：同一来源按 `标题归一化 + 链接` 去重；跨来源按 trgm 相似度 ≥ 0.6 合并为同一"话题簇"，记录在哪些来源出现、最高排名，用作热度加权。
5. 采集到的标题生成向量（复用 `content_embedding` 的嵌入服务；没有配置嵌入模型时退化为关键词 + trgm）。

### 3.4 验收标准

- `OPS_CRAWL_MODE=off` 或强度为"关闭"时，运行 24 小时（用假时钟）出站请求数为 0（HC-21）。
- 修改间隔为 5 分钟时保存失败并提示"最短 10 分钟"。
- 模拟目标返回 429，来源立即进入暂停，超管收到通知；暂停期间不再请求。
- 模拟目标 robots 禁止，适配器不请求该路径。
- 请求中不含 `Cookie`、`Authorization` 头；UA 为固定值（HC-23）。
- 本地开发（`OPS_DEV=1`）使用 mock 热榜服务（挂在 :8091），测试不访问真实网站。
- 敏感平台：在假时钟下连续提交 200 个小红书链接，24 小时内实际请求数不超过当档每日上限，相邻请求间隔不小于当档最小间隔，夜间时段请求数为 0。
- 敏感平台：mock 返回验证码页，该平台立即停 24 小时；7 天内第二次触发后开关自动变为关闭。

### 3.5 小红书笔记与公众号文章的读取（EX-T-05，S2）

- **用途**：①对标参考：看同赛道做得好的笔记 / 文章用了什么标题、结构、选题角度、发布时间；②热点补充：其他来源里出现的小红书、公众号链接，补充标题和摘要后参与热点匹配。
- **链接从哪来**（因为系统不做平台内搜索和列表发现）：
  1. 用户在账号运营方案的"对标"里手动添加笔记或文章链接（单条或多行粘贴，每次最多 20 条，进入读取队列）；
  2. 用户在快速收集、灵感收件箱里粘贴的链接（勾选"读取页面"才入队）；
  3. 热榜、RSS、聚合、联网搜索结果中出现的小红书 / 公众号链接（只对与某账号相关度 ≥ 75 的条目入队）。
- **读取什么**：

| 字段 | 小红书笔记 | 公众号文章 |
| --- | --- | --- |
| 标题、作者昵称、发布时间 | 读 | 读 |
| 正文文字 | 读（公开页可见部分） | 读 |
| 话题标签 | 读 | — |
| 页面上公开显示的互动数（点赞、收藏、评论数） | 读（若免登录可见） | 不读（公众号阅读数需要微信客户端，不可得） |
| 图片 | 只记图片数量，不下载 | 不下载 |
| 评论内容、评论者信息、作者主页其他内容 | **不读** | **不读** |

- **正文怎么用**（防止"洗稿"，F-104、R-PL-02）：
  1. 读取后立即调用 `reference_analyze` 提炼结构化要点：标题结构、开头钩子类型、段落结构、选题角度、话题标签、可借鉴点；**页面只展示提炼结果和原文链接**。
  2. 原文正文只保存 7 天（用于重新提炼），之后删除，只保留提炼结果。
  3. 原文正文**不进入起草、改写的上下文**，只有提炼结果可以作为"参考结构"注入；同质化检查新增"与已读取参考文本的相似度"，超过阈值在检查页提示。
  4. 对标结果不属于素材库（素材库只放用户自己的真实经历和来源可查的资料）。
- **交互**：账号"运营"页新增"对标参考"区块：添加链接 → 显示排队位置和预计读取时间（按限额计算，例如"第 6 个，预计今天 15:40 前"）→ 读取完成后显示提炼卡片。读取失败显示原因（"需要登录才能查看""触发验证，平台读取已暂停至明天 10:20""robots 不允许"），并提供"手动粘贴正文"作为兜底，粘贴后走同样的提炼流程。
- **数据**：`reference_item`（workspace_id、account_id、platform、url、状态 queued / done / failed / blocked、title、author、published_at、metrics jsonb、body_text（7 天后置空）、analysis jsonb、error、queued_at、fetched_at）。
- **AI 契约 `reference_analyze`**：输入正文（截取前 4000 字）与平台；输出 `{"title_pattern":"","hook_type":"","structure":[""],"angle":"","tags":[],"takeaways":[""]}`；约束：只总结方法，不复述原文句子（输出中与原文连续重合超过 15 字视为校验失败并重试）。
- **验收标准**：读取队列严格遵守敏感平台限额；第 8 天正文字段为空而提炼结果仍在；起草接口的上下文中不出现参考正文（单元测试检查 `context_refs`）；遇到登录墙时状态为 `blocked` 且平台暂停。
- **红线检查**：不登录、不绕过、不读评论和个人信息；正文不进入创作上下文。

## 4. 起号定位与运营大纲（模块 Q）

### EX-Q-01 账号运营方案（S1）

- **用户故事**：作为运营者，我新建一个账号时，想让 AI 根据我的领域、经历和目标，给出两三个可选的定位方案；选定后，这份方案成为这个账号所有 AI 推荐的依据。
- **方案包含的字段**（`account_strategy`）：

| 字段 | 说明 |
| --- | --- |
| 赛道 `niche` | 一句话，例如"互联网大厂职场新人成长" |
| 目标读者 `audience` | 画像：年龄段、身份、痛点、阅读场景 |
| 差异化 `differentiation` | 和同类账号相比"为什么关注你"，必须基于用户提供的真实经历或资源 |
| 人设 `persona` | 与现有 `persona_tone` 合并 |
| 内容支柱 `pillars` | 3–5 个，每个有名称、说明、占比（合计 100%）、示例选题 3 个 |
| 发布节奏 `cadence` | 每周几篇、偏好星期、每篇形态（长图文 / 图文笔记 / 漫画） |
| 阶段 `stage` | `cold_start` 起号（0–1 个月）/ `growth` 成长 / `stable` 稳定；不同阶段推荐策略不同（第 6 节） |
| 目标 `goals` | 可选：例如"3 个月 1000 关注"；只用于展示和复盘对比，不驱动任何自动动作 |
| 对标账号 `benchmarks` | 用户手填名称、"我欣赏它什么"，以及若干代表作链接；代表作链接按第 3.5 节低频读取并提炼，不抓取账号主页列表 |
| 追踪关键词 `keywords` | 用于热点匹配，AI 生成初稿 |
| 禁区 `taboo` | 不碰的话题，例如"不写情感八卦" |

- **交互**：
  1. 账号页新增"运营"标签页，包含四块：运营方案、内容大纲、今日热点、今日推荐。
  2. 没有方案时显示"起号向导"，三步：①问卷（领域、你有哪些真实经历和资源、想吸引谁、每周能投入多少时间、平台和形态、可选：粘贴旧作品）；②AI 生成 2–3 个方案并排对比，每个方案说明适合理由与风险；③选一个，逐字段编辑，**点"启用方案"才保存**。
  3. 已有方案时，显示当前方案 + "调整方案"按钮。调整时 AI 会参考近 30 天复盘数据和热点表现，给出修改建议（逐条接受）。
  4. 方案有版本历史；启用新版本后，旧版本保留可查看、可恢复。
  5. 方案中的人设、读者、禁用词会同步到现有 `account_profile`（显示"将同步以下字段"，人确认）。
- **AI 契约 `account_positioning`**：
  - 输入：问卷答案、平台与形态、可选旧作品摘要（沿用 bootstrap 的截取规则）、可选赛道热点快照（最近 7 天与问卷领域相关度最高的 20 条热点标题）。
  - 输出：`{"options":[{"niche":"","audience":"","differentiation":"","persona":"","pillars":[{"name":"","desc":"","ratio":30,"examples":["",""]}],"cadence":{"per_week":3,"days":[1,3,5],"format":"image_note"},"keywords":[],"taboo":[],"fit_reason":"","risks":[""]}]}`。
  - 约束：差异化必须引用问卷中的真实经历，不得编造身份、头衔、经历；支柱占比合计 100；方案之间要有实质区别。
- **验收标准**：只填问卷不粘贴作品也能生成方案；不点"启用"数据库无变化；方案版本可恢复；同步档案字段需二次确认。
- **红线检查**：AI 只给草稿（UX-03）；对标只读取用户给出的单篇链接，不抓取账号主页。

### EX-Q-02 内容大纲（月 / 周）（S1）

- **交互**：

- **红线检查**：逐槽采用；"计划发布日"不是定时发布。

## 5. 每日热点（模块 R）

### EX-R-01 账号热点匹配（S1）

- **用户故事**：我每天打开某个账号，想看到今天和它相关的热点，以及每条能怎么写。
- **流程**：
  1. **粗筛（规则，不花钱）**：从最近 24 小时的 `hot_item` 中，按向量相似度（账号关键词 + 支柱描述 vs 热点标题）和关键词命中，取前 40 条；命中屏蔽词或方案禁区的直接排除。
  2. **精排（AI，经济档模型）**：把 40 条交给 `hot_relevance`，返回相关度、理由、切入角度、风险标签；保留相关度 ≥ 60 的，最多 15 条。
  3. 结果写入 `account_hot_match`（按账号 + 日期），当天再次打开直接读库。
- **触发**：见第 6.3 节"每日生成"参数；另有"刷新"按钮（冷却 10 分钟）。
- **交互**（"今日热点"区块，同时在工作台作战台显示前 3 条）：
  1. 每条显示：标题、来源与排名（多来源合并时显示"微博第 3、百度第 8"）、上榜时长、相关度、"为什么和你有关"、建议切入角度、风险标签、原文链接。
  2. 操作：**转为选题**（逐条，打开选题编辑框预填角度，人确认后入库，source=`hot`，记录 `hot_item_id`）、**不感兴趣**（记录反馈，用于后续匹配）、**打开原文**。
  3. 带高风险标签的条目灰显，"转为选题"按钮禁用并提示原因。
  4. 页面顶部显示数据状态："数据来自 微博、百度，最近更新 09:20"；采集关闭时显示"热点采集未开启，以下为模型根据常识给出的时效话题（请自行核实）"，并保留现有的"粘贴资讯"入口。
- **AI 契约 `hot_relevance`**：
  - 输入：账号方案摘要（赛道、读者、支柱、禁区）、候选热点列表（id、标题、来源、排名、可选摘要）、近 14 天该账号"不感兴趣"的热点标题。
  - 输出：`{"items":[{"hot_item_id":"","relevance":0,"reason":"","angle":"","risk":["disaster"]}]}`。
  - 约束：只能使用输入中的热点 id；不得补充榜单之外的事件细节；不相关就给低分，不要硬凑。
- **验收标准**：mock 热榜中放入 3 条与账号强相关、1 条灾难类，匹配结果前 3 名为强相关条目，灾难类带风险标签且无法转选题；二次打开不重复调用模型。
- **红线检查**：逐条转选题（H-01）；不对外推送。

### EX-R-02 热点趋势与赛道雷达（S2）

- 账号热点页增加"近 7 天"视图：按话题簇显示在榜时长和排名曲线，帮助判断"还来得及写"还是"已经过气"。
- 每个话题簇显示"本工作区其他账号是否已在写"（防止同工作区账号同质化，呼应 R-PL-02）。
- 纯规则，不调用模型。

- 现有 `POST /topics/hot-suggest` 保留接口不变：采集开启时，提示词改为"基于以下真实热点（附 id 和链接）"并自动注入当日账号热点匹配前 10 条；采集关闭时行为与现在一致。
- 删除提示词中的"禁止使用或模仿任何平台热榜爬取结果"，改为"只能使用输入中的热点，不得编造"。

## 6. 每日作品推荐（模块 S）

### EX-S-01 今日推荐（S1）

- **用户故事**：我每天打开账号，想直接看到"今天写什么"，并知道 AI 为什么这么推荐。
- **推荐数量**：主推 = 当天在节奏中是否是发布日（是：1–2 条；否：1 条，用于储备），另给 2 条备选；数量可在账号运营设置里改（1–5）。
- **推荐来源与权重**（规则先算候选，再交给 AI 写成选题卡）：

| 来源 | 说明 | 起号期权重 | 成长 / 稳定期权重 |
| --- | --- | --- | --- |
| 大纲槽位 | 今天或近 3 天有已采用但未开写的槽位 | 高 | 高 |
| 支柱轮换 | 近期哪个支柱写得最少 | 高（起号期要先把支柱写全） | 中 |
| 账号热点 | 当日相关度 ≥ 75、无高风险标签 | 低（起号期少追热点，先立住定位） | 高 |
| 素材驱动 | 素材库中最近新增、尚未被引用、与某支柱相关的素材 | 中 | 中 |
| 复盘驱动 | 近期表现最好的作品对应的支柱 / 标题结构（来自 `metric_snapshot` 与复盘采纳记录） | 低（数据少） | 高 |
| 选题池 | 已采用但没开写、或待定选题中评分高的 | 中 | 中 |

- **交互**（"今日推荐"区块 + 工作台作战台顶部卡片）：
  1. 每条推荐是一张结构化选题卡（沿用 EX-C-01 字段：标题、角度、目标读者、钩子、需要的素材、形态），外加**推荐理由**和**依据标签**（"支柱：职场沟通 · 热点：微博第 5 · 素材 2 条"），依据可点击跳转。
  2. 操作：**采用为选题**（逐条；入库 source=`daily`，可选同时设计划发布日为今天）、**直接开始写**（= 采用 + 新建作品，进入编辑器；核心观点输入框保持为空，只显示角度提示，H-02）、**换一个**（重新生成这一条，记录放弃反馈）、**不感兴趣**。
  3. **不提供"全部采用"**。
  4. 推荐卡显示生成时间；当天热点更新且出现明显更相关的热点时，区块顶部提示"有新的热点，可重新生成"，不自动替换。
- **AI 契约 `daily_recommend`**：
  - 输入：方案摘要、阶段、今天日期与是否发布日、规则候选（每个候选带类型和 id：槽位 / 支柱 / 热点 / 素材 / 复盘结论 / 选题）、最近 30 篇标题、生效中的账号记忆。
  - 输出：`{"items":[{"title":"","angle":"","audience":"","hook":"","needed_materials":[],"format":"","reason":"","basis":[{"type":"hot","id":""},{"type":"pillar","name":""}],"primary":true}]}`。
  - 约束：每条至少一个 `basis`；`basis` 只能引用输入中的 id；不得编造热点细节和用户经历；不与近 30 篇重复。
- **数据**：`daily_recommendation`（账号、日期、条目 jsonb、ai_call_id、生成时间）+ `daily_recommendation_action`（条目序号、动作 adopted / started / replaced / dismissed、topic_id、操作人）。动作同时写入 `ai_feedback`，进入现有记忆闭环。
- **验收标准**：同一账号同一天不重复生成（除非人点"重新生成"）；每条推荐都有可跳转的依据；采用后选题池出现该选题且字段完整；"直接开始写"后观点框为空。
- **红线检查**：H-01（逐条入库）、H-02（观点人写）、UX-05（无批量）；不创建发布动作。

### EX-S-02 推荐效果回看（S2）

- 复盘页新增"推荐采用情况"：近 30 天推荐数、采用率、采用后发布的作品表现与非推荐作品对比；按来源（热点 / 支柱 / 素材）分组。
- 这些数据回流到 `daily_recommend` 的候选权重（规则调整，不训练模型）：某类来源连续两周采用率低于 10%，自动降低其权重，并在方案页提示。

### 6.3 每日生成的触发方式（参数）

| 参数 `daily.generate` | 说明 | 成本 |
| --- | --- | --- |
| `off` | 不自动生成，用户在"运营"页手动点"生成今日推荐 / 匹配今日热点" | 最低 |
| `on_open`（推荐默认） | 当天第一次打开该账号的运营页或工作台时生成；生成在后台任务中进行，页面先显示"正在准备今日推荐"，完成后刷新 | 只为真正被打开的账号花钱 |
| `background` | 每天固定时间（默认 07:00，可改）在后台为"近 7 天有人打开过"的账号生成，打开即可看 | 较高；跳过不活跃账号 |

- 设置位置：工作区设置（全工作区默认）+ 账号覆盖。
- 后台生成走现有 `ai_job` 任务池，受每个工作区并发数和用量上限约束（10 文档 3.5、用量上限）；超过当日用量上限时跳过并在通知中心提示。
- 成本估算（每账号每天）：`hot_relevance` 1 次（约 3–4k token 输入）+ `daily_recommend` 1 次（约 4–6k token）。按经济档模型，单账号每天约 0.02–0.1 元；10 个账号每月约 6–30 元。

## 9. AI 任务契约汇总

| 任务类型 | 模型档位 | 触发 | 输入要点 | 输出 | 校验 |
| --- | --- | --- | --- | --- | --- |
| `account_positioning` | 标准 | 起号向导 / 调整方案 | 问卷、可选旧作品、赛道热点快照 | 2–3 个方案 | 支柱 3–5 个且占比和为 100；差异化必须引用问卷原文中的经历关键词 |
| `strategy_revise` | 标准 | 调整方案 | 当前方案、近 30 天作品与指标、推荐采用情况 | 逐条修改建议 `{"changes":[{"field":"","from":"","to":"","reason":""}]}` | 字段名必须是方案字段 |
| `strategy_outline` | 经济 | 生成大纲 | 方案、空槽位、选题池、近期标题、热点 | 槽位建议 | 日期必须是输入槽位；热点 id 必须存在 |
| `hot_relevance` | 经济 | 每日 / 刷新 | 方案摘要、候选热点、负反馈 | 相关度 + 理由 + 角度 + 风险 | id 必须来自输入；relevance 0–100 |
| `daily_recommend` | 标准 | 每日 / 重新生成 | 方案、阶段、规则候选、近期标题、记忆 | 推荐选题卡 | 每条至少一个 basis 且 id 有效；条数符合设置 |
| `reference_analyze` | 经济 | 对标页面读取完成 / 手动粘贴 | 正文前 4000 字、平台 | 标题结构、钩子、段落结构、角度、标签、可借鉴点 | 与原文连续重合不超过 15 字 |

全部沿用 `runAIJSON` 的"校验失败重试一次"、用量记录、`context_refs` 可解释（UX-10：推荐卡上可以看到"参考了哪些热点、素材、记忆"）。模型提示词在 `prompt_template` 中可编辑，并补充 `prompt_eval_case`（EX-P）。
