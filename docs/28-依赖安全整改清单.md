## 2. 逐条评估

### 2.1 chi：客户端 IP 可伪造（server，直接依赖）

**漏洞**：`ClientIPFromXFF` 直接信任 `X-Forwarded-For`，攻击者可伪造客户端 IP（CVSS 4.8）。

**仓库现状**
- `server/internal/app/server.go:137` 使用 `middleware.RealIP`（同类信任逻辑）。
- `server/internal/app/httpx.go:179` 有自研 `clientIP()`，同样取 XFF 第一段。
- `clientIP()` 的消费方：`auth.go` 的 `audit(...)`（登录成功/失败）与 `session` 记录的登录 IP。
- 部署侧 `deploy/nginx-ops.conf`、`deploy/nginx-ops-https.conf` 都设置了 `X-Forwarded-For $proxy_add_x_forwarded_for`。

**判断**：升级 chi 只能关掉它自己的 helper；**本仓库的 `clientIP()` 一字未改，伪造 IP 依然成立**。影响面是审计日志与登录 IP 失真（不是提权）。若将来接限流/风控，这会变成绕过手段。

**建议动作**
1. `cd server && go get github.com/go-chi/chi/v5@v5.5.0 && go mod tidy`。
2. 另立一项（与升级解耦）：仅在显式配置可信代理（如 `OPS_TRUSTED_PROXIES` CIDR）时采信 XFF，否则用 `RemoteAddr`；`clientIP()` 与 `middleware.RealIP` 二选一，不要两套并存。
3. 若后续改用 chi 的 `ClientIPFromXFF`，必须传可信代理参数（新版签名要求）。

**验证**：`go build ./... && go vet ./...`；手工构造带 `X-Forwarded-For: 1.2.3.4` 的登录请求，确认审计表 `ip` 字段在默认配置下为真实回环地址而非 1.2.3.4。

**代价**：低（minor，无 API 删除）。**风险**：低。

### 2.2 react-router：开放重定向（两端，传递依赖，有真实接触面）

**两条 advisory**
- `GHSA-wrjc-x8rr-h8h6`：`<Link>` / `useNavigate` 通过**反斜杠**实现开放重定向，是 CVE-2025-68470 的绕过（CVE-2026-53669）。
- `GHSA-337j-9hxr-rhxg`：SSR hydration 的 `deserializeErrors()` 任意构造函数注入（CVSS 6.1）。

**仓库现状**
- 两端均锁 `react-router-dom@6.30.6`（6.x 最新版，**该线无修复**）。
- 无 SSR：`web/src` 与 `desktop/renderer-src/src` 中不存在 `hydrateRoot` / `deserializeErrors` / `StaticRouter` → **第二条不适用**。
- 第一条**不是纯理论**：`web/src/lib/agent-markdown.tsx:59` 的守卫是
  `href.startsWith('/') && !href.startsWith('//')`，**没有拦反斜杠**；`href` 来自模型输出的 Markdown，随后 `navigate(href)`。`/\evil.com` 这类值能通过该守卫，在 6.30.6 上可能被当成外站跳转。
- 桌面端同一份代码（`desktop/renderer-src/src/lib/agent-markdown.tsx:59`）。

**建议动作**
1. **先做（不依赖升级）**：把内部链接判定改为「必须是 `/` 开头、第二个字符不是 `/` 或 `\`、不含控制字符」，并在 `safeHref()` 做同样限制；补一条单测覆盖 `/\evil.com`、`//evil.com`、`/%5Cevil.com`。
2. **再升级**：`react-router-dom` `6.30.6 → 7.18.x`（≥7.18.0）。v7 中 `react-router-dom` 仍可作为兼容入口，但官方建议逐步改用 `react-router` 的导出。
3. 升级后回归全部路由（两端各 466 处 `Link`/`navigate` 调用），重点：登录跳转 `?next=`、工作台深链、桌面端 hash/history 差异。

**验证**：两端 `typecheck` + `test:unit` + `build`；E2E 全量；手工构造带 `/\` 的模型输出链接，确认不再弹出站外。

**代价**：中高（major + 全站路由回归）。**风险**：中。

### 2.3 @tiptap/core：`mergeAttributes()` 原型污染（两端，传递依赖）

**漏洞**：`mergeAttributes()` 把自有 `__proto__` 键转成继承的可执行 DOM 属性（GHSA-cp6q-959q-f8rh，无 CVE，CVSS 未评分）。

**仓库现状**
- 两端锁 `@tiptap/* 2.27.3`。
- 唯一使用点：`web/src/components/section-editor.tsx:201`，扩展固定为
  `StarterKit / Link / AssetImage / Placeholder / Markdown`，且 `Markdown.configure({ html: false })`。
- 全仓库未见把**外部可控属性**传给 `mergeAttributes` 的自定义扩展；内容以 Markdown 文本进入编辑器，不解析 HTML。

**判断**：当前暴露面低（需要恶意扩展或把不可信属性塞进 schema）。但 2.x 无修复版，会长期挂在告警里。

**建议动作**
1. 升级 `@tiptap/core` 及同族（`pm` / `react` / `starter-kit` / `extension-image` / `extension-link` / `extension-placeholder`）到 `≥3.30.4`，**两端同时升**，避免两份锁文件版本漂移。
2. 3.x 属大版本，需按官方迁移说明核对：`StarterKit` 选项、扩展包导入路径、`Markdown` 扩展（第三方 `tiptap-markdown`）的兼容性——**这一条是升级里最可能卡住的点**，先单独验证该扩展在 3.x 下可用再全量升。
3. 升级前不要改 `html:false`，这是当前最主要的缓解措施。

**验证**：编辑器回归——输入、粘贴（文本/HTML/图片）、Markdown 序列化再解析、BubbleMenu、协作草稿保存；`typecheck` + `test:unit` + `build` + 相关 E2E。

**代价**：中（major）。**风险**：中（第三方 `tiptap-markdown` 可能与 3.x 不兼容）。

## 4. 验收与回滚

- 每批单独提交，提交信息写清「升级前 → 升级后」版本号与告警号（如 `#11`）。
- 本地复核：
  ```bash
  cd server && go list -m github.com/go-chi/chi/v5
  cd web && pnpm why react-router && pnpm why @tiptap/core
  cd desktop/renderer-src && pnpm why react-router && pnpm why @tiptap/core
  ```
- 测试基线（当前已知状态，别当成自己改坏）：
  - `go vet ./...` 通过；
  - `go test ./internal/app` **有 20 项既有顺序依赖失败**（HEAD 同样红，见 docs/08「回归基线核查」），升级后用「失败名单是否变化」判断，而不是要求全绿；
  - `web` 与 `desktop/renderer-src`：`typecheck` 0 错、`test:unit` 分别 45/45 与 41/41、`build` 通过。
- 回滚：单批 `git revert` 即可；**不要手工编辑锁文件**，用包管理器重新生成。
- 关闭判定：Dependabot 告警自动关闭 + 上述本地复核命令输出正确版本；两者都满足才在本文档记「已关闭」。
