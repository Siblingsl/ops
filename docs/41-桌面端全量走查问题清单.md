### Q-19 · CX 构建与并发 PATCH 撞 PostgreSQL 40001 序列化失败，漏出 500（P2，**fixed**）
- **复现**：`POST /works/{id}/builds` 与 `PATCH /works/{id}` 真并发（Promise.all，同 token 同时发），构建事务 RepeatableRead 首读 work 行后 PATCH（`touchContent` 改 `revision/updated_at`）先提交 → 构建事务 commit 时 `could not serialize access due to concurrent update (SQLSTATE 40001)` → 未捕获，响应 500 `internal`"服务器内部错误，请稍后重试"。多轮采样 10/10、6/10、8/10 稳定复现（服务端日志累计 35 次 40001 ERROR）。
- **证据**：`proto-r9-concurrent.mjs` S5 块终轮 `frozen=0 patchFirst409=0 e500=10 other=0`；ops-e2e-r9b.log `ERROR 请求处理失败 route=/api/v1/works/{id}/builds err="ERROR: could not serialize access ... (SQLSTATE 40001)"`。
- **根因分析（读码确认）**：`cx_builds.go:232` 的 `pg_advisory_lock(hashtextextended("cx-build-create:"+workID))` 只串行化 **build-vs-build**；PATCH 侧（`works.go:164 touchContent`，经 PATCH work / updateSection 调用）不取同一把锁。`cx_builds.go:244` 事务用 `RepeatableRead`，RR 下写冲突在 **commit 时**才报 40001；cx_builds.go 四处 `tx.Commit`（:350/:388/:797/:1078）均未捕获转译。对照：同仓 8 处 CX 路由（`cx_account_analysis_http.go:743`、`cx_visual_plan_http.go:669` 等）已按 `pgErr.Code == "40001"` → 409 `version_conflict` 处理，builds 族漏配同款模式。
- **影响面**：编辑器自动保存/PATCH 与用户点"生成排版"并发时构建请求 500（前端展示"服务器内部错误"）；事务回滚不损坏数据，但违反 FR-CX-02"源变化 409"的契约语义——本应得到明确"作品已修改，请刷新后重新创建构建"的用户被引导重试而不是刷新。
- **建议修复方向**：cx_builds.go 四处 commit 及 `cxBuildSourceSnapshot` 返回路径统一加 `errors.As(err, &pgErr) && pgErr.Code == "40001"` → 409 `version_conflict`（文案对齐 `cx_builds.go:431` 既有"作品已修改，请刷新后重新创建构建"），与同仓 8 处既有模式一致；或 PATCH 侧 touchContent 取同键 advisory lock（改动面更大，不推荐）。补一条并发 PATCH×build 的回归测试。
- **状态：fixed（2026-11-23）**。`server/internal/app/cx_builds.go`：新增 `cxBuildCommit(tx, ctx)` 把 RepeatableRead 事务 commit 的 40001 统一转 409 `version_conflict`（"作品已修改，请刷新后重新创建构建"），三处 build commit 全部改走 helper；`createCXBuild` 包装事务体，首读 `FOR UPDATE` / INSERT 外键检查在并发 PATCH 先提交时**当场**抛出的 40001 同样转 409；`cxCurrentBuildSourceHash` 只读快照 commit 40001 → 409"作品正在修改，请稍后重试"。
  验证：`go test ./internal/app -run TestCX02BuildVersusConcurrentPatchSerializesAsConflict -count=1 -v` **PASS（0.32s）**：6 轮 build×PATCH 真并发，build 仅出现 201/409、409 均为 `version_conflict`、按最新 revision 重试均 201，**0 次 500**。

### Q-27 · 桌面业务窗 200% 文本放大键盘路径不生效（P3，**fixed**）
- **复现**：真实 Electron 业务窗（OPS_DESKTOP_DEV_URL 模式）内 Ctrl+=（Ctrl+Plus）连按 4 次 → `devicePixelRatio` 恒 1.0、`body` fontSize 恒 16px、内容尺寸不变；同一路径在浏览器（Web 端）原生生效。
- **预期 vs 实际**：docs/16 §15.3 要求验收"200% 文本放大"；键盘用户（WCAG 1.4.4）在桌面窗内没有可用的页面缩放路径。
- **证据**：`ui-r10c-zoom-dpi.mjs` 运行时探针（放大前后 outerWidth/innerWidth/dpr/fontSize 快照）；编译产物 `desktop/.build/main.js` 读码——应用菜单含 `role:'zoomIn'/'zoomOut'/'resetZoom'`（"放大/缩小/实际大小"），但全文件无 `before-input-event`、无 `globalShortcut`、无 `webContents.setZoomLevel` 调用。
- **根因分析（读码确认）**：菜单 role 的缩放加速键在 Windows 上依赖标准菜单栏路径；业务窗菜单收纳于自绘标题栏（DesktopTitlebar），Ctrl+= 不经菜单加速键触发。设置窗与 offline 失败窗未单独排查，可能同样缺失。
- **影响面**：桌面端键盘用户失去 200% 文本放大路径（系统 DPI 缩放仍可用作替代放大手段）；Web 端不受影响。
- **建议修复方向**：业务窗 `webContents` 注册 `before-input-event` 拦截 Ctrl+=/Ctrl+-/Ctrl+0 映射 zoomLevel（与菜单 role 行为一致），并同步核查设置窗/local view 与 offline 窗；修复时补一条真实 Electron 缩放 E2E 断言（放大后 dpr 或内容字号变化）。
- **状态：fixed（2026-11-23）**。`desktop/src/main.ts`：新增 `installWebContentsZoomShortcuts(contents: WebContents)`——`before-input-event` 仅处理 `type==='keyDown'`、`control && !alt && !meta && !shift` 的 `+`/`=`（+0.5）、`-`（-0.5）、`0`（归零），档位 clamp ±5，`event.preventDefault()` 后 `contents.setZoomLevel`；业务窗创建处调用，本机设置窗（local view）同样安装（offline 失败窗未装，保持原样）。
  验证：`node --test test/zoom-shortcuts.test.cjs` **3/3 PASS**（Ctrl+=/-/0、clamp ±5 与修饰键不误触、两窗安装源码契约）。
  真实 Electron E2E：`renderer/e2e/desktop-window-zoom.spec.ts` **1 passed（13.6s）**——启动真实业务窗，用 Electron 原生 `webContents.sendInputEvent` 注入 Ctrl+=/Ctrl+-/Ctrl+0，断言 zoomLevel 0→0.5→1→0.5→0，且 zoomLevel=1 时 `devicePixelRatio` > 初始 ×1.15（真实放大效果）。
  方法说明（如实登记）：2026-11-23 探针实测 **Playwright CDP `keyboard.press` 不触发 Electron `before-input-event`**（一个事件都收不到），故 E2E 改用 Electron 官方 `sendInputEvent` 注入原生键盘事件；物理键盘走同一 `before-input-event` 链路。
